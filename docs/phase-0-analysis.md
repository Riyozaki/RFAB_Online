## 2. История версий: поддерживался ли 1.5.97

**Вывод: официально — нет.** Доказательства из истории репозитория:

1. Коммит `e84ef59d` (2022-04-16, до релиза v1.0.0) «Multi game version support for script extender» ввёл константу `kSKSEMinBuild` с комментарием `// AE+ only // Use this to raise the SKSE baseline` и строку ошибки `Pre anniversary Script Extender is unsupported`.
2. Диалог ошибки Address Library с мая 2022 (`eeb67e81`) требует `All in one (1.6.X)` — `Code/client/main.cpp:18`.
3. `README-ANIMATION-MODS.md` форка rwf: «Tested extensively with Skyrim Version 1.6.1170.0. It might work with the earlier 1.640+ versions… barely been tested». Про 1.5.97 — ничего.
4. Поиск `1.5.97` по всей истории всех веток: **0 совпадений**. Ветка `feat-modded-anim-compat-1.5.0` — это версия **мода STR 1.5.0**, а не игра 1.5.97 (ложный след, фиксирую явно).
5. Upstream ушёл ещё дальше: коммит `6f963497` «SSE 1.7.99 and SKSE changes» (формат Address Library v5, новые структуры) — в HEAD форка rwf **не входит**; вливать его нельзя.

Хронология версионных переходов (теги = версии мода STR, не игры):

- v1.0.0 (2022-07) — игра 1.6.353;
- коммиты `553793fc` «fix: Skyrim new update crashes» и `2436384e` «fix: TESObjectCELL layout in 629 update» — переход на игру 1.6.629 (сент. 2022), **менял раскладки структур** (см. §3.3);
- v1.5.0 (2023-04) — игра 1.6.640;
- v1.6.1+ (2023-12+) — игра 1.6.1130/1170; отдельных «структурных» коммитов перехода поиском не найдено, но в этот период добавлены новые RE-структуры боя (`CombatController`, `CombatGroup`, `MagicTarget` и др.), у которых в репозитории нет исторического эталона для старых версий игры.

Состояние веток форка rwf: `features-integration` — ветка по умолчанию, полностью включает `dev` (0 коммитов dev впереди), на 84 коммита впереди `master`; анимационная совместимость (`feat-modded-anim-compat`, `feat-unlimited-behavior-vars`) в неё **влита**. Рекомендуемая база — именно она, замороженная на `a7d06156` (решение №1 в конце).

## 3. Что завязано на версию игры и объём порта на 1.5.97

Проект **не использует CommonLibSSE**. Версионная привязка состоит из пяти слоёв:

### 3.1. Загрузчик базы адресов — НЕСОВМЕСТИМ по двум мелочам (исправимо малой кровью)

- Клиент читает `Data/SKSE/Plugins/versionlib-<версия>.bin` и требует `format == 2` (`Code/client/VersionDb.h`, `VersionDb::Load` — имя файла собирается как `versionlib-%d-%d-%d-%d.bin`).
- В RFAB база SE называется **`version-1-5-97-0.bin`** и имеет **format = 1** (проверено по реальному файлу: версия 1.5.97.0, модуль `SkyrimSE.exe`, 778 674 записи).
- Я прогнал на этом файле точную копию алгоритма декодирования из `VersionDb.h`: декодировалось **до последнего байта без рассинхронизации** (max offset `0x35F3830`). То есть формат полезной нагрузки совместим; нужны только: принять `format 1` и имя `version-*` (или копирование файла при установке). Это Фаза 1, пункт первый, обратимо конфигом не требует.

### 3.2. Address Library ID — все на месте (главный результат разведки)

Адреса клиент получает через `VersionDbPtr`/`POINTER_SKYRIMSE` (макрос в `Code/client/Utils.h:7`). Сверка скриптом `tools/address_db_check.py` исходников HEAD с базой 1.5.97 из RFAB:

- **278/278** ID функций/глобалок присутствуют;
- **2806/2806** RTTI ID (`Code/client/Games/Skyrim/RTTI.cpp`) присутствуют;
- отсутствующих: **0**.

Оговорки честности: наличие ID означает «в базе Meh для 1.5.97 есть соответствующий оффсет». Это **не доказывает** тождество сигнатур функций и раскладок структур — они аудируются отдельно (§3.3–3.4). ID между релизами стабильны (проверено: `TESForm::GetById = 14617` одинаков в v1.0.0/v1.5.0/v1.6.5/HEAD; с v1.5.0 добавилось всего 33 новых ID — все есть в базе 1.5.97).

### 3.3. Раскладки структур — главный риск порта

175 заголовков игровых структур в `Code/client/Games/Skyrim/**`, 243 `static_assert`, 85 проверок `sizeof`. Доказанный пример версионного сдвига (коммит перехода на 1.6.629 `553793fc`):

| Структура | 1.6.353 (v1.0.0) | 1.6.629+ … HEAD |
|---|---|---|
| `TESObjectREFR` | `0x98` | `0xA0` |
| `Actor` | `0x2B0` | `0x2B8` (все поля после точки вставки +8) |
| `PlayerCharacter` | `0xBE0` | `0xBE8` |
| `TESObjectCELL` | менялся отдельно (`2436384e`) | |

1.5.97 **старше** 1.6.353, поэтому как минимум эти структуры в HEAD для 1.5.97 неверны (поля после вставки читались бы со сдвигом +8 — краши/порча памяти). Сколько ещё структур различается между 1.5.97 и 1.6.353 — **из этого репозитория не видно** (история начинается с AE). Метод Фазы 1: сверка полей с SE-веткой CommonLibSSE (1.5.97) как с независимым эталоном + точечная проверка дизассемблером по вашему exe там, где эталоны расходятся. Объём аудита: 85 `sizeof`-структур и все виртуальные таблицы (в структурах объявлены порядки virtual-функций, напр. `Actor::sub_9C…`; добавление виртуалок между версиями игры сдвигает индексы — отдельная категория аудита).

### 3.4. Внутрифункционные оффсеты патчей — почти гарантированно неверны на 1.5.97

Места, где код патчит **середину** функций (смещение от адреса Address Library зависит от компиляции конкретного exe). Полный список живых мест (найден поиском, не выборочно):

| `Games/Skyrim/BSSystem/BSTaskletManager.cpp:35` | `+0x63` SwapCall |
| `Games/Skyrim/Interface/UI.cpp:126,131,136` | `+0x682` SwapCall, `+0xFE` Put `0xEB`, `+0x15` Put `0x9090` |
| `Games/Skyrim/Interface/Menus/MapMenu.cpp:13-15` | Nop `+0x53`, `+0x9D`, `+0x9F` |

Каждое место в Фазе 1: либо подтвердить по дизассемблированию 1.5.97, либо заменить на паттерн-скан с проверкой байтов (fail-safe: не совпало — не патчить и писать в лог, а не крашиться). Заодно: два «абсолютных адреса» 1.6.x (`0x1411F0FD4` в `BSThread.cpp`, vtable `0x1416244D0` в `TESObjectREFR.cpp`) находятся в `#if 0`/комментариях — **не живые**, но при порте их нельзя «оживлять».

### 3.5. SKSE и лаунчер

- `Code/client/ScriptExtender.cpp`: ищет DLL по имени `skse64_<версия exe>.dll`, грузит `LoadLibrary` и дёргает экспорт `StartSKSE`. Порог `kSKSEMinBuild = 20100`: при формуле `maj*10^6+min*10^4+rev*100+bld` SKSE 2.0.20 даёт 2 002 000, то есть проверка формально **проходит** — блокировка «AE+ only» по арифметике не срабатывает. Это вывод из чтения кода, **требует проверки в игре** (реальные поля FileVersion у `skse64_1_5_97.dll` из RFAB стоит снять заранее). Отдельно проверить, что SKSE 2.0.20 экспортирует `StartSKSE` (снимается `dumpbin /exports` за минуту — в чек-лист Фазы 1).
- Лаунчер мапит exe сам: `ExeLoader` — generic PE loader, `SteamCeg` — дешифровка Steam-защиты конкретного билда. Для Steam 1.5.97 **требует проверки**; для GOG/Downgrade-вариантов поведение может отличаться (вопрос №4). Поле `exeDiskSz = 35410264` в `TargetConfig.h` объявлено, но не используется (мёртвое).
- Сообщение пользователю при отсутствии базы жёстко говорит про 1.6.X (`main.cpp:18`) — в Фазе 1 заменить на явную проверку «ровно 1.5.97» с понятной ошибкой, как требует задание.

### 3.6. Что от версии НЕ зависит

Сервер целиком (не знает версию игры; плагины читает `es_loader`-ом по файлам), протокол/сериализация, UI (CEF/Angular), `SkyrimTogether.esp` и Papyrus (формат esp/pex 1.5.97 совместим), дескрипторы поведений как текстовые данные (но хэши поведений считаются по фактическим HKX клиента, см. §5).

## 4. Синхронизация сегодня: архитектура и найденные слабые места

Модель: сервер — реле + хранилище состояния (EnTT), симуляция NPC — на клиенте-«владельце» (`OwnerComponent`, передача — `RequestOwnershipTransfer/Claim`, `NotifyOwnershipTransfer`). Движение: снапшоты владельца раз в **100 мс** (`CharacterService::RunLocalUpdates`), на приёме — `InterpolationSystem`. Формы адресуются серверным `GameId` (канонический ModId по имени плагина + BaseId; ESL `0xFE` обрабатывается — `ModSystem.cpp`). Аутентификация требует точного равенства `BUILD_COMMIT` клиента и сервера (отдельной версии протокола нет — при изменениях протокола в Фазе 1 введу явный `kProtocolVersion`). Квесты: партийная модель, приоритет лидера, доработка «member advancement» влита из ветки `fix/Rework-PR-769…`, misc-квесты за флагом `Gameplay:bEnableMiscQuestSync=false`.

Конкретные находки по коду (не «мнения», а места):

1. **Баг знака серверного HP.** Клиент шлёт урон как отрицательную дельту (`Actor.cpp`: `HealthChangeEvent(..., -realDamage)`), получатели применяют `current + Delta`, а сервер хранит `current - Delta` (`Code/server/Services/ActorValueService.cpp`, `OnHealthChangeBroadcast`, рядом TODO «should server side health not be updated?»). Серверная копия HP при уроне **растёт**; она же используется при сериализации спавна для поздно вошедших. Кандидат на «враг воскрес/полный HP у нового игрока». Влияние подтвердить тестом в Фазе 2 до фикса.
2. **Нет проверки владельца** в серверном `ActorValueService`: значения/max-значения/дельты HP принимаются от любого клиента и ретранслируются (вид `view<..., OwnerComponent>` строится, но владелец не сверяется). Источник рассинхрона и «войны за NPC» (в истории форка есть фикс «naked NPCs», сам автор пишет, что первопричина — fighting over NPC ownership).
3. **XP-синхронизация зачаточная** (`Gameplay:bEnableXpSync`, по умолчанию вкл.): хук `HookAddSkillExperience` (`PlayerCharacter.cpp`) считает дельту только боевых навыков, клиент раз в 1 с шлёт сумму **только если в партии**; сервер шлёт остальной партии; получатель начисляет на **свой** `LastUsedCombatSkill` (не тот навык, что у заработавшего; при `-1` опыт теряется). Нет идемпотентности, нет подтверждения, кэш обнуляется до отправки-подтверждения. Для RFAB этого недостаточно вдвойне (см. §5.3).
4. Мёртвый `ValidateAuthParams` (всегда `false`, не вызывается по назначению) и путаница имён `bEnableModCheck` («Bypass the checking…» при `false` по умолчанию и `kLocked`). Проверка модов (ModPolicy) по умолчанию выключена; при включении серверу нужны файлы плагинов в `mods/` для `RecordCollection`.
5. TODO/FIXME/HACK в `Code/`: 116 строк, из них FIXME 9 — сконцентрированы в QuestService («FIXME EXPERIMENT» вокруг сцен/сбросов). Upstream issues, релевантные нам: #810 «Remote actors sometimes can't draw their weapon and just stand still», #866 краш sleep/wait/fast travel offline, #835 залипание imagespace-эффектов у удалённых игроков.
6. Логирование: spdlog есть на клиенте и сервере; ротации/уровней на модуль в конфиге не нашёл — задача Фазы 1 по ТЗ.

## 5. RFAB: что внутри (по репозиторию сборки)

RFAB — портативная MO2-сборка: 46 модов-папок (+5 сепараторов), ядро свёрнуто в один мод `RFAB` (`RFAB.esp` 31 МБ, 1367 `.pex`, свой `RFAB.dll`). Профиль-шаблон (`MO2/profile-template/Default`): **23 плагина** в loadorder, из них light — только `TrueHUD.esl`. Исторический `plugins0.txt` показывает происхождение: Requiem + Apocalypse + DeadlyDragons/UltimateDragons + модули `RFAB XP/ClassSystem/Origins/Deadlands/…`, ныне влиты в `RFAB.esp`. Внимание: template может отставать от фактического профиля пользователя — финальный эталон брать с рабочей установки.

Подтверждено из файлов: SKSE **2.0.20** (`skse64_1_5_97.dll`, readme «currently 1.5.97»), Address Library SE (format 1), Nemesis **v0.84** (PatchLog от 2026-05-21, патч-коды `cbbi, hthsf, kbrtsf, rtsf, thta, tkuc`), NetScriptFramework (существует только под 1.5.97 — жёсткий лок версии всей сборки).

### 5.1. Нативные плагины (инвентаризация по папкам MO2)

~61 SKSE DLL + 4 NSF DLL. Критичные для мультиплеера группы:

- **Движковые патчи:** SSE Engine Fixes (+tbb в корне), Bug Fixes SSE (NSF), Scrambled Bugs, Actor Limit Fix (NSF), ActorBasePerkFix, AnimationQueueFix, BashBugFix, EnchantmentReloadFix, po3_* фиксы, BackportedESLSupport. Риск: двойные хуки тех же функций, что и STR (напр. аллокатор форм: STR `Games/Memory.cpp HookFormAllocate` ↔ Engine Fixes; в форке есть ветки `fix/EngineFixes-FormAllocator`, `fix/EngineFixes-v7-support`, но они про AE-линейку Engine Fixes — для SE-версии поведение **требует проверки**).
- **Анимационный стек:** Nemesis, Animation Motion Revolution, **OpenAnimationReplacer**, BehaviorDataInjector, PayloadInterpreter, DtryKeyUtil. STR синхронизирует behavior-переменные по хэшу графа (`Code/client/ModCompat/BehaviorVar`, дескрипторы в `GameFiles/.../SkyrimTogetherRebornBehaviors/`, 32 существа). Для RFAB придётся сгенерировать/добавить дескрипторы под фактические Nemesis-поведения сборки; OAR-подмены условны и локальны — при одинаковой сборке у всех клиентов визуально сойдутся, но условия на несинхронизированном состоянии дадут косметический рассинхрон; PayloadInterpreter применяет эффекты по anim-событиям локально — на чужих акторах возможно двойное применение (аудит Фазы 5).
- **Геймплейные DLL:** `RFAB.dll` (CommonLibSSE-NG плагин сборки: Papyrus-функции `RFAB_PapyrusFunctions`, свои меню уровня/перков, combat hit spells, bash-хуки — по строкам бинаря; исходников нет, **чёрный ящик**), CustomSkills, DifficultyBalance (переопределяет кривые урона сложности — прямо взаимодействует с Фазой 3 и с серверным `uDifficulty` STR), SkyrimSoulsRE (меню без паузы), RaceMenu/skee64 (морфы/скульпт STR не синхронизирует — FaceGenSystem покрывает базовый FaceGen, не RaceMenu sculpt), DismemberingFramework (отключён в шаблоне), HookDamage/FloatingDamage (UI урона, локальны), Skyrim Outfit System, TrueHUD, QuickLootIE (лут-интерфейс — взаимодействие с синхронизацией контейнеров проверить).
- **Papyrus-инфраструктура:** PapyrusUtil (StorageUtil — в нём, вероятно, живёт счётчик XP, см. ниже), po3 PapyrusExtender, DbSkseFunctions, PAPER, ConsoleUtilSSE и др. Сами по себе мультиплееру не мешают, но скриптовые эффекты поверх них синхронизируются только в объёме STR (MagicService/призыв/проектайлы).

### 5.2. Квесты/контент RFAB

`RFAB.esp` — реквiem-наследие: де-левел мир, переписанные перки/заклинания/акторы, свои квесты (Origins, Deadlands, BountyHunt, Fall Of The Thieves Guild по спискам), боссы (`RFAB_TurtleBoss`, Deadlands tower boss и т.п. по именам скриптов), драконы с enrage-скриптами (`RFAB_Script_Dragon_Enrage`). Всё это формы одного esp — с точки зрения GameId/FoID-согласования ситуация **простая** (23 плагина, порядок фиксирован шаблоном), а с точки зрения скриптовой логики — синхронизируются только стадии квестов/сцены по модели STR; RFAB-скрипты, считающие, что игрок один (`GetPlayer()`), на владельце актора сработают «как обычно», на остальных клиентах их эффекты должны подавляться механизмами STR (PapyrusService) — полнота подавления проверяется только в игре по чек-листу.

### 5.3. Опыт в RFAB (определяет Фазу 4)

По строковым таблицам `RFAB_XP_Handler.pex` / `RFAB_XP_Alias.pex` (исходников `.psc` в сборке нет, кроме одного файла):

- Уровень персонажа растёт **не от использования навыков**, а от XP: убийства (`RegisterForActorKilled` SKSE-событие → `OnActorKilled` → `CalculateXP` по уровню и расе жертвы), квесты (`OnQuestComplete`, таблица `Quests.ini`: имя квеста → XP), книги (`BaseBookXP=200`), боссы (+1000 по имени из `BossList.json`).
- Таблицы: `RaceList.json` (раса→база XP, ключи — русские имена), пороги уровней `Experience.ini` (1→500 … 50+→155000), настройки `RFAB_XP_Settings.json`, множитель `MultiplierXP` (глобал), капы `CapLevel/CapLevelImperial`, исключение по кейворду `NoXPKeyword`, проверки `IsValidXPKill/IsPlayerOwnedKiller/IsPlayerTeammate`.
- Применение: манипуляции `fXPLevelUpBase/fXPLevelUpMult` + `SetPlayerLevel`, перк-поинты при `OnLevelIncrease`, UI через Scaleform-вызовы. Где именно хранится накопленный XP (вероятно StorageUtil, ключ `_PlayerXP` в строках) — **точно не установлено**, нужна декомпиляция двух pex (Champollion) или ответ автора.
- Отдельно: **Custom Skills Framework** — свои деревья (Classes, AedraChampion, Lich, Survival, Vampire, Werewolf; конфиги NSF), прогресс вне ванильных ActorValue. И ванильные навыки как таковые (их XP STR хукает — см. §4.3).

Итог для Фазы 4: равный XP всем = реплицировать **события-основания** (убийство серверного актора один раз, завершение квеста один раз) и начислять каждому клиенту через его собственный RFAB-пайплайн, либо считать сумму на сервере по тем же таблицам (файлы таблиц у сборки текстовые — сервер может читать те же). Вариант выберем после декомпиляции хендлера; оба за конфиг-флагом.

## 6. Предварительный план работ (приоритеты и риски)

Общие правила по ТЗ соблюдаю: всё новое — за серверными флагами (`Console::Setting`, секция в существующем механизме конфига сервера; стиль имён как у существующих `Gameplay:*`), протокол — с явным повышением версии, коммиты атомарные.

**Фаза 1 — порt 1.5.97 и стабилизация** (критический путь; без неё остальное не тестируется):
1. Импорт кода в `Riyozaki/RFAB_Online` с сохранением истории (решение №2), ветка от `features-integration@a7d06156`.
2. `VersionDb`: format 1+2, имя `version-*`/`versionlib-*`, явная проверка «только 1.5.97» с человекочитаемой ошибкой + лог распознанной версии/SKSE.
3. Аудит структур: откатить/выделить под `TP_SKYRIM_1597` изменения 1.6.629 (REFR/Actor/PlayerCharacter/CELL), сверить 85 sizeof-структур и виртуалки с CommonLibSSE-SE; список расхождений — отдельным документом.
4. Все 15 внутрифункционных патчей (§3.4): верификация по exe 1.5.97 или паттерн с fail-safe.
5. SKSE-лоадер: проверка `StartSKSE` и FileVersion `skse64_1_5_97.dll`, порог заменить явным whitelist 2.0.20.
6. Сборка: Linux — сервер+тесты здесь; Windows — инструкция и ваша машина (BUILD.md). Логи: уровни уже есть (spdlog), добавлю ротацию и префиксы модулей сервера.
   Риск: объём структурного аудита непредсказуем до первой сверки; митигация — сначала «запуск до главного меню + подключение к локальному серверу» как milestone, структуры чинить по краш-логам NSF.

**Фаза 2 — синхронизация**: фикс знака HP (после подтверждающего теста), проверка владельца в ActorValueService, аудит передачи владения (клетка/дисконнект/расстояние) по существующим сообщениям, приоритизация уже частично есть (SendToPlayersInRange), снапшоты 100 мс — измерять, а не переписывать вслепую.

**Фаза 3 — HP-масштаб** (сервер — источник истины):
- Конфиг: `Gameplay:bEnablePartyHealthScaling`, таблица множителей строкой/JSON в серверном конфиге, по умолчанию `1→1, 2→3, 3→4, N→N+1`. Число врагов/спавн/левел-листы **не трогаем вообще** — в коде STR спавном управляет клиент-владелец через обычную загрузку ячеек, серверного спавнера нет, требование «не зависит от числа игроков» выполняется отсутствием механизма (зафиксирую тестом-наблюдением).
- Точки: серверный `ActorValuesComponent` (max HP) при AssignCharacter/Spawn и при смене N: `newCurrent = newMax * (oldCurrent/oldMax)`, никогда не воскрешать мёртвых, не применять к игрокам и (конфигурируемо) к призванным/важным NPC. Клиентам — существующими `NotifyActorMaxValueChanges` (ForceMode::PERMANENT) + коррекция текущего через damage-канал; процентные эффекты движка считаются от AV, поэтому ломаться не должны, но пороговые скрипты боссов RFAB — в чек-лист.
- Что такое N — **решение №3** (сервер/партия/игроки в ячейке боя). Юнит-тесты формулы и пересчёта доли — на сервере без игры.

**Фаза 4 — опыт**: сначала декомпиляция `RFAB_XP_Handler/Alias` и карта хранения XP; затем серверные идемпотентные события (`KillCredit{serverId жертвы}` один раз, `QuestComplete{quest GameId}` один раз на партию/сервер), начисление всем по выбранной области (решение №3 заодно), конфиг `Gameplay:bRfabXpShare`, защита от дублей при реконнекте (журнал выданных событий на сервере в пределах сессии + дедуп по id). Ванильный skill-XP STR оставить как есть, но исправить потерю при `LastUsedCombatSkill == -1` отдельным флагом.

**Фаза 5 — RFAB-профиль**: `Gameplay`/ModPolicy пресет «RFAB» (ModCheck вкл., список 23 плагинов на сервере, хэш-чек loadorder при коннекте — расширение AuthenticationRequest полем хэша списка плагинов, с повышением версии протокола), дескрипторы поведений, финальная матрица совместимости по результатам тестов, чек-листы 1/2/3/4 игрока из ТЗ.
