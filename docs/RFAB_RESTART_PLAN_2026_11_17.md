# RFAB: проверка чистого старта и план адаптации

**Дата:** 2026-11-17. **Статус:** исходный аудит; все пункты реализации впоследствии одобрены.

> Решения после согласования находятся в разделе 9 и имеют приоритет над историческими
> предложениями об этапных игровых тестах, сокращении объёма и открытыми вопросами ниже.
> Описание исходного снимка не является состоянием текущего дерева; фактическая реализация и
> доказательства — в `RFAB_REBUILD_WORKLOG.md` / `RFAB_RELEASE_STATUS.json`.

Игровой код, конфигурация, версия и сборочные сценарии в этой сессии не изменялись. `origin/main` получен через `git fetch`; текущая рабочая ветка уже содержит актуальный `Riyozaki/RFAB_Online/main`. Другой репозиторий изучался по отдельному временному снимку, без переключения веток и без переноса его кода в этот репозиторий.

## 1. Краткий вывод

Рекомендуемая основа дальнейшей работы — **RFABTogether с зафиксированным свежим STR + портом 1.5.97**, а не очередная масштабная переделка старого `main`. Переписывать сетевое ядро STR с нуля оснований нет. Старые версии, включая v3.1.7, нужны как справочник поведения и источник отдельных проверяемых исправлений, а не как пакет для массового cherry-pick.

При этом **«чистый upstream» не означает «исправная игра»**: дополнительные пробы на неизменённом серверном коде нового репозитория воспроизвели обратный знак обновления серверного HP и повторное изъятие последнего предмета с отрицательным остатком. До RFAB-механик нужен небольшой этап исправления и проверки базовых контрактов.

Это целевой аудит связанных подсистем, а не построчная проверка всей кодовой базы и не диагностика конкретной игровой сессии. Skyrim в этой среде не запускался; без логов двух клиентов нельзя приписать описанные зависания одной доказанной причине.

## 3. Конкретные находки

### P0-1. Обратный знак изменения серверного HP — воспроизведено

В новом `Code/server/Services/ActorValueService.cpp:108`:

```cpp
storedHealth = currentHealth - message.DeltaHealth;
```

Клиент создаёт дельту урона как `-realDamage` (`Actor.cpp:976/989/1000`), дельту лечения как положительное значение и применяет сетевую дельту **прибавлением** (`client/Services/Generic/ActorValueService.cpp:298`).

Изолированная копия штатного harness была дополнена пробами; **ни один production-файл и исходный штатный harness не менялись**. Пакеты прошли настоящий serializer/deserializer и серверные обработчики:

```text
[AUDIT] damage: before=120 delta=-10 expected=110 server=130.0
  FAIL AUDIT finite damage decreases server HP
[AUDIT] healing: before=120 delta=+10 expected=130 server=110.0
  FAIL AUDIT finite healing increases server HP
```

Это доказанное расхождение **серверного кэша** с клиентской семантикой. Из этого нельзя без игры заключить, что каждый удар визуально лечит NPC: клиенты дополнительно получают другие обновления. Но полагаться на такое серверное состояние для назначения нового владельца, late join, масштабирования и наград нельзя.

Минимальная следующая работа после согласования: регрессионные тесты finite damage/heal, затем локальная правка контракта и отдельная проверка взаимодействия абсолютных HP с дельтами. Одного изменения знака недостаточно, чтобы объявить весь бой исправленным.

### P0-2. Повторное изъятие последнего предмета — воспроизведено

`server/Services/InventoryService.cpp:85` без проверки остатка вызывает `Content.AddOrRemoveEntry(message.Item)`. В `encoding/Structs/Inventory.cpp` удаление отсутствующей записи добавляет новую запись с отрицательным количеством.

Проба: у общего NPC одна вещь; Alice изымает её, затем Bob в той же ячейке посылает допустимое изъятие с актуальной ownership epoch:

```text
[AUDIT] loot: initial=1 afterAlice=0 afterBob=-1 second-take-broadcasts=1
  FAIL AUDIT second concurrent take is rejected without a negative stack
```

Подтверждено: второй take не отклонён, возникает отрицательный стек и отправляется уведомление. Само появление двух вещей в настоящих клиентских сумках этой пробой не проверялось; отсутствующая арбитрация создаёт для него условия. Нужен контракт **переноса** предмета, а не только ограничения отрицательных чисел.

### P0-3. README и серверный INI описывают уже удалённую систему

Новый `VERSION` — 5.0.0-alpha.1, но README продолжает обещать v4.1.2, 318 тестов, 23 серверных сцены, общий XP, E-revive и согласованные сейвы. Фактически штатных core cases — 27, серверных сценария — 3, RFAB-сервисы удалены.

В поставляемом `STServer.ini` остались, например, `bEnableDownedSystem`, `bEnableCoordinatedSaves`, `bEnableQuestXpSingleAward`, `bEnablePersonalMerchantStock`, `fHealthMultiplier`, `bAutoScaleEnemyHealth`, `bEnableDesyncDetector`. В актуальном `Code/` нет ссылок на эти ключи. Нельзя рассчитывать, что их переключение управляет чистой alpha.

`run-static-checks.sh:37–41` также явно исключает фактический аудит hook discipline / actor lifetime для upstream-кода, оставляя self-test самих инструментов. Это осознанное ограничение покрытия, а не доказательство прохождения этих двух аудитов.

### Наблюдение о зависаниях старого main

В старом `common/Authority/Lease.cpp:52` pinned-entity проверяется раньше already-owner. Сервер при отказе шлёт `NotifyRelinquishControl` (`server/Services/CharacterService.cpp:1374+`), а клиентский обработчик (`client/Services/Generic/CharacterService.cpp:1896+`) способен убрать `LocalComponent` и поставить `Remote` без отдельного запрета для собственного 0x14.

Это опасная цепочка, совместимая с симптомом «свой персонаж перестал двигаться». Для диагноза конкретной сессии нужно доказать по логам, что claim/relinquish действительно прошёл для собственного аватара. Не переносить в чистый upstream весь старый механизм владения ради исправления этой цепочки: в чистой базе он другой.

| Удалённый игрок — обычный незащищённый NPC | Неполно: upstream уже вызывает `SetPlayerRespawnMode()` для remote player при спавне и восстановлении (`CharacterService.cpp:661,1701`). Нужно синхронизировать downed-переход и проверить AI, а не просто ещё раз выставить essential |

## 5. Предлагаемый объём первой играбельной RFAB-адаптации

Цель — сначала **два игрока вместе в одной области**, обычный бой, ранения/подъём, одинаковая награда XP, HP врагов ×2, общий лут и защищённое хранилище. Не включать одновременно миграцию хоста, общий сон/повозки, весь произвольный Papyrus, тактический HUD, все моды анимаций и все скриптовые боссы.

Сохранять STR как ядро. Знание RFAB держать в небольших адаптерах: ранения/бой, прогрессия, хранилища, совместимость. Сетевое состояние и чистые правила отделить от вызовов движка. Новый код не должен обрастать вторыми владельцами HP, инвентаря или персонажей.

На клиенте движок и ECS меняются в основном потоке; в очереди передаются ID/handles и поколение мира, не долговечные сырые указатели. Сервер ведёт групповые состояния и арбитрацию, но **не симулирует Skyrim AI**: AI выполняется назначенным клиентом.

Новые RFAB-возможности требуют явного согласования версии протокола/возможностей клиентов. После их добавления совместимость с обычным upstream или старыми RFAB-клиентами не предполагается. Проверять совпадение сборок и модпака до начала сессии.

### 5.1. Ранение и подъём

Предлагаемая машина состояний:

```text
Alive -> Downed -> Reviving -> Recovering -> Alive
                   | cancel     | engine confirmation
                   +-> Downed   +-> bounded failure handling
```

- На колене можно ждать неограниченно; обычное лечение, зелья и реген не дают самоподъём. Не отключать ради этого весь инвентарь/систему эффектов и не обнулять HP циклом каждый кадр.
- Нативный вход и выход из bleedout — однократные переходы. Не спамить `bleedoutStart`, `SetWeaponDrawn(false)`, `StopCombat/StartCombat`.
- Сервер распространяет состояние с revision; late join получает текущий snapshot. Remote-клон должен реально перейти в согласованный bleedout, а AI-владелец — знать, что цель downed. Отсев downed-цели и одноразовая переоценка допустимы; вечный restart combat — нет.
- Свой аватар никогда не становится удалённым NPC. Изменение цели врага не равно передаче его симуляции другому клиенту. Падение игрока само по себе не требует массовой передачи всех NPC, если его клиент продолжает исправно симулировать мир.
- Удерживается назначенная клавиша взаимодействия (E по умолчанию, а не жёсткий код клавиши). Предлагается **5 секунд**; смысл фразы владельца про 5 секунд пока требует подтверждения.
- Сервер ведёт время; проверяет группу, downed/ready, свежесть позиции, один выбранный reviver, дистанцию; открытие меню/отпускание/уход/падение reviver отменяют попытку. Начальный ориентир дистанции — 3 м, отмена за 3.5 м. Сервер не имеет navmesh Skyrim и не может сам доказать проходимость/видимость.
- После подъёма ориентир — 40% HP и 3 секунды защиты, без возможности атаковать под защитой. Эти цифры — предложение, не подтверждённое решение владельца. Подъём завершается после подтверждённого выхода движка из bleedout, не после записи положительного HP в том же кадре.
- Essential/no-recovery, REQ global и изменённые настройки восстанавливаются к сохранённым прежним значениям после корректного выхода из кооп-режима. Disconnect на колене имеет отдельный путь восстановления, чтобы не оставить одиночную игру запертой.

### 5.2. HP врагов ×2

На двоих нужен именно **×2**, не старая формула ×3. В первой версии множитель фиксируется для боя; подключение/выход игрока не лечит босса и не меняет ему HP посреди удара.

- Это увеличение согласованного max HP, а не дополнительное деление урона пополам: иначе меняются смысл HUD, скриптовые пороги и взаимодействия RFAB.
- Хранить исходное HP и scale version на конкретную жизнь существа; не умножать повторно текущее значение при каждом спавне/ownership transfer.
- При передаче владельца сохранять абсолютное состояние и корректную долю HP, не пересоздавать инвентарь и AI.
- Не масштабировать автоматически игроков, союзников, призывы, мирных NPC и все объекты выше произвольного порога HP. Для скриптовых боссов отдельно проверить абсолютные пороги и многофазность.
- Не менять одновременно количество врагов, сопротивления, урон и выбранную RFAB-сложность. Масштабирование вводится отдельно после проверки немодифицированного боя.

### 5.3. XP: событие награды, а не изменение кошелька

В прочитанном RFAB `ModXP()` меняет `PlayerXP` и вызывает `VanilaXPGain()`. `CalculateXP()` применяет множитель и округляет вниз до кратного 5. `RFAB_Menu` отдельно расходует PlayerXP на навыки. Книжная награда зависит от уровня читателя. Это объясняет, почему баланс кошелька не является журналом наград.

Предлагаемый контракт:

1. Распознанное событие RFAB (`kill`, `quest reward`, `XP book`, `custom reward`) получает стабильный ID и контекст.
2. Сервер фиксирует сумму и получателей. Персонаж на колене остаётся участником и получает награду; AFK в другом подземелье — не получает по предлагаемой политике участия.
3. Каждому участнику выдаётся одна согласованная награда. Повторная доставка идемпотентна; входящее начисление не порождает новое исходящее событие.
4. На клиенте награда проходит адаптированный путь RFAB для обоих XP-хранилищ и нужных уведомлений, а не слепую запись в `pSkills->data->xp` без побочных эффектов.
5. В режиме RFAB отключается именно дополнительная STR-рассылка опыта навыка через LastUsedCombatSkill, не вся личная прогрессия.

Ключи: убийство — entity identity + incarnation/death sequence, не BaseId расы; задание — quest + конкретная награда/цикл повторения, не только стадия; книга — стабильная форма + согласованная политика одноразового чтения. `Infamy` допустим как совместимый локальный suppression-маркер, не как сетевой идентификатор.

Источник данных — небольшой явный bridge на границе выдачи RFAB с контекстом источника, либо другой подтверждённый семантический callback. Одного перехвата `ModXP(int)` без источника тоже недостаточно. Исходники/ABI `RFAB.dll` и Bizarre Adventure отдельно проверяются; «поддерживает любые моды автоматически» не обещать. Поллинг кошелька можно оставить для диагностики, не выдачи.

Не синхронизировать балансы кошельков: игроки тратят их независимо. «Одинаково» относится к наградам, а не остатку или готовому уровню. Нужно уточнить **одинаковая базовая награда с личными множителями или одинаковая итоговая цифра**; это разные правила. Первое сохраняет личные RFAB-бонусы, второе требует согласованного группового множителя/расчёта.

При загрузке чекпоинта журнал наград и фактический XP должны откатываться согласованно. При рестарте нельзя обещать exactly-once без сохранённых receipt-ов/журнала. В первой версии автоматический XP-догон после переподключения выключить.

### 5.4. Обычный лут, торговцы и защищённые городские сундуки

Разделить классы хранения явно:

| Класс | Политика первой версии |
|---|---|
| Сундук с добычей / труп | Общее содержимое, сервер решает допустимый перенос |
| Защищённый сундук RFAB | **Общее хранилище группы/кампании**, доступное из разрешённых точек |
| Торговый ассортимент и золото торговца | Пока личные, чтобы не ломать локальные RFAB/StorageUtil-скрипты |
| Конфискованные вещи и личные квестовые хранилища | Не превращать в общие |
| Сумка игрока, навыки, личные бонусы | Личные |

`RFAB_SecureChestScript.OnActivate` вызывает `SecureChest.Activate(player)`. Надо разрешить реальную целевую ссылку из свойств скрипта/проверенных привязок. Городской объект — точка доступа; скрытый контейнер — хранилище. Нельзя исключить его просто за нахождение вне текущей клетки или раздать ему разные ID для каждого города. Но нельзя и объединить разные целевые контейнеры без проверки свойств в RFAB.esp.

Для такого хранилища обычная STR-модель «объект текущей клетки» недостаточна: сервер удаляет object entities после ухода последнего игрока (`ObjectService::OnPlayerLeaveCellEvent`). Нужен долговечный ключ `(campaign/group, canonical storage ref)`, независимый от загруженной клетки и временного EnTT ID. Два игрока могут открывать разные точки доступа в разных городах.

Нужны operation ID, revision, проверка остатка и единая серверная фиксация переноса **из источника в получателя**. Начать можно с одного активного писателя контейнера; QuickLoot и AutoLoot не должны обходить эту арбитрацию. Не блокировать основной поток игры ожиданием сети. Простой постфактум `RemoveItem(BaseId)` не безопасный универсальный rollback.

Дополнительно: корректный bootstrap и явный импорт старых личных вещей (не перезаписывать данные первого/второго игрока), сохранение сервера, перезапуск, журнал, модифицированные предметы и extra data, запрет передачи неподдерживаемой динамической формы без потери предмета. Для обычных контейнеров — регистрация на доступе, bounded queue до ответа, соседние exterior cells и очистка всех привязок при disconnect/load. Число «3 секунды» — timeout с контролируемым отказом, не основание терять действие молча.

## 6. Вайп: A как базовый режим, B как отдельная экспериментальная возможность

**Главное различие:** A — восстановление участников и незавершённого столкновения; B — настоящий откат временной линии мира. A нельзя называть полным rollback.

### A. Reset encounter, без Load Save

- В помещении — проверенный вход/точка сбора; не безусловная телепортация за любую ближайшую дверь.
- **В открытом мире — последняя подтверждённая безопасная точка до начала столкновения**, без боя/падения/загрузки, с проверкой земли и допустимого места. Одна смена exterior cell не означает новую безопасную точку.
- Точка фиксируется при начале боя. Участники получают соседние безопасные позиции, а не одну координату внутри стены/воды/ловушки. Нет валидной точки — понятный отказ/ручной выбор, не телепорт в ноль.
- Вайп считается сервером для согласованной группы участников столкновения; чужой игрок на сервере не влияет. Политику для напарника, ушедшего далеко, надо согласовать явно. Не телепортировать другого игрока из Вайтрана только потому, что в ином данже кто-то упал.
- После согласованного отсчёта (предлагается 5 секунд) участники восстанавливаются; живые враги этого столкновения получают восстановление HP и однократный сброс состояния боя у текущего AI-владельца. Новые входящие события старого encounter generation не применяются к восстановленному состоянию.
- Уже убитые враги не воскрешаются, добыча/задания/потраченные расходники не откатываются. Отсюда остаётся стратегия «убить часть комнаты, упасть, добить остаток». Если это неприемлемо, нужен настоящий checkpoint/B или специальная поддержка конкретной арены.
- Снятие опасных эффектов и снарядов — целевое; не применять `DispelAllSpells` ко всему персонажу с потерей RFAB-пассивок. Скриптовые арены/фазы не объявлять resettable без отдельной проверки.

### B. Checkpoint reload, опция после стабильного A

Это **не один сейв хоста для всех**. У каждого свой `.ess` и связанный `.skse` от одной согласованной транзакции checkpoint. Хранить manifest: checkpoint ID, участники/персонажи, сборка, модпак, серверное состояние соответствующего момента.

```text
Prepare -> Quiesce all -> Disconnect + confirmed teardown
        -> Load each player's matching save
        -> all clients Ready in a new world generation
        -> restore matching server state -> reconnect/resume
```

- Кнопка Disconnect сама по себе не доказывает завершение teardown. Должны быть отсечены входящие пакеты, отложенные engine tasks, callbacks и старые bindings; обработать ошибку загрузки/обрыв на каждом шаге.
- Состояние сервера, прогрессия/receipts и общее хранилище восстанавливаются в ту же точку. Иначе можно сохранять добычу в общем банке и бесконечно получать её вновь после rollback.
- Сам checkpoint создаётся только после подтверждённой записи всех нужных файлов и manifest. Предыдущая корректная пара сохраняется; обычные одиночные сохранения и чужие файлы не удаляются и не «лечатся» автоматически.
- Если checkpoint признан недоступным **до начала Load у кого-либо**, можно выбрать A при наличии валидного anchor и поддержки encounter.
- Если один клиент уже загрузился, а другой нет, автоматический A поверх двух разных миров недопустим: остановить возобновление сессии, предложить согласованное восстановление/ручную загрузку.
- Не сбрасывать весь серверный мир из-за одной группы, если сервер допускает независимые группы. Для MVP проще один campaign/cohort.

Ни A, ни B не имеют гарантии «0% CTD». Промежуточные игровые проверки обязательны. Если доступен только один плейтест в конце, объём релиза нужно сократить, а не считать модельные тесты заменой игры.

## 7. Порядок работ и приёмка

В таблице — **предложение**, не обещание, что этапы уже сделаны.

| Этап | Содержание | Что должно быть доказано до следующего |
|---|---|---|
| 0. Зафиксировать базу | SHA STR/порта, версии клиента/сервера, RFAB manifest, действующие настройки, убрать ложные обещания README/INI; сохранить установщик и сборщик отчёта | Чистая воспроизводимая сборка с точным build ID, понятный откат |
| 1. Базовый обмен | Сначала тесты и локальные исправления HP sign/дублирования HP и последнего предмета; инвариант своего аватара | Production-path tests + Windows build; вдвоём видят друг друга, двигаются, NPC имеют оружие/атакуют, HP сходится после передачи и reconnect |
| 2. RFAB death/revive | Essential/REQ bridge, downed snapshot, AI target, 5-секундный подъём после согласования | Самоподъём невозможен; оба клиента видят раненого; враги бьют стоящего; отмены/два reviver/late join/disconnect корректны |
| 3. Encounter A | Безопасные anchors в интерьере и exterior, согласованный reset | Переход exterior-cell не портит anchor; оба падают, один падает далеко, обрыв, неподдерживаемая арена дают определённый результат |
| 4. Прогрессия и HP ×2 | Семантический XP bridge, reward IDs/receipts, оба XP-пула; отдельно масштаб HP | Два одинаковых по сумме события не схлопываются, одно не платится дважды; downed получает XP; ownership не удваивает max HP |
| 5. Контейнеры | Довести транспорт переносов, QuickLoot/AutoLoot, общий secure storage, persistence | Одна вещь — один получатель; разные города и рестарт не теряют банк; торговцы не затронуты; crash/retry не дюпают |
| 6. Checkpoint B | Отдельная опция, согласованный manifest и цикл teardown/load/resume | Проверены отказы каждого шага, несколько повторных загрузок, восстановление банка/XP/world одной точки; частичная загрузка не возобновляет сессию |

Каждый этап: небольшой дифф с одним изменением поведения, тест реального пути, зелёная сборка клиента и сервера, установщик из того же SHA, короткая игровая проверка обоими участниками, затем следующий шаг. Пробы HP и лута — хороший пример: проходившие штатные тесты не покрывали неверные контракты.

### Минимальная матрица игры

1. Два новых кооп-сейва, встреча/движение/бой; две разные роли владельца NPC; 2H, лук и магия.
2. Вход/выход через дверь и границу exterior cells; быстрые клики QuickLoot до регистрации.
3. Ранение владельца NPC и не-владельца; второй атакует/лечит, цель переключается без агро-цикла.
4. Revive cancel, одновременно два запроса, меню, high latency, disconnect и late join.
5. Две одинаковые XP-награды рядом по времени, отложенный Papyrus, книга/квест/kill, переподключение.
6. Два AutoLoot на один труп; единственный зачарованный предмет; личный торговец; общий защищённый сундук из разных городов и после рестарта.
7. Вайп в данже и в открытом мире; нет anchor; босс со скриптом фазы; частичный disconnect.
8. Для B отдельно: отсутствующий/чужой/неполный checkpoint, load fail у одного клиента, старые пакеты, общий банк до/после rollback. До этого B выключен.

Логировать переходы, а не каждую итерацию: build/world/encounter ID, entity incarnation, AI owner/epoch, downed revision, reward ID и причина начисления/отказа, transfer ID/revision. Сборщик отчёта должен собирать точные установленные версии и логи обоих клиентов плюс сервера. Подробную постоянную телеметрию и автоисправление всех расхождений в MVP не вводить.

## 8. Решения владельца и открытые вопросы

Уже принято из сообщения: A базовый, B опциональный; враги ×2 HP, не ×2 спавнов; равная награда XP участникам; неограниченное ожидание на колене; городские защищённые сундуки общие.

До реализации достаточно подтвердить:

1. **Пять секунд** — это длительность удержания для подъёма, отсчёт до общего reset, либо оба таймера? Предложение: оба по 5 секунд, ожидание помощи без лимита.
2. **Одинаковый XP** — одинаковая база с личными RFAB-множителями или строго одинаковое итоговое число? Также согласовать участие: одинаковая encounter-группа, а не любой онлайн в другом городе. Число участников первой версии предлагается ограничить двумя.
3. **Какая установленная RFAB**: точная редакция/версия, включён ли Bizarre Adventure; можно взять manifest из отчёта установщика/сборщика. Публичные скрипты Prime не доказывают побайтовое совпадение с установленной Respect/иной редакцией.

Следующее действие после согласования — этап 0–1 в выбранной чистой базе, **не** массовый перенос старой обвязки и **не** одновременная реализация всех пунктов.

## 9. Утверждённая политика реализации (после аудита, 2026-11-17)

Владелец одобрил реализацию **всего** согласованного объёма. Выпускается **один полный
переписанный кандидат**, после чего проводится **один совместный игровой тест в конце**.
Промежуточные игровые релизы и поиск второго игрока между этапами не требуются. Внутренняя
последовательная разработка, отдельные коммиты, CI-артефакты и автоматические fault-тесты допустимы.
Это заменяет требования разделов 6–8 к промежуточным игровым тестам и предложенное там
сокращение объёма при единственном итоговом плейтесте. Модельные тесты не выдаются за Skyrim.

Окончательно принято:

- Essential/native downed, **без лимита ожидания**, пока остаётся живой товарищ.
- Удержание revive **5 секунд**, отсчёт group wipe также **5 секунд**.
- A — основной encounter reset/retreat с проверяемыми pre-combat anchors, включая outdoor.
  B — отдельная опциональная настоящая coordinated checkpoint load; частичный Load не допускает
  автоматического A поверх расходящихся миров.
- XP — одинаковая **базовая** награда участникам; множители RFAB остаются личными, кошельки
  и покупки независимы. Не синхронизировать баланс и не угадывать награды по его изменению.
- Враги — **×2 HP на двоих**, не ×3 и не удвоение спавнов.
- Обычный лут — настоящий арбитраж source→recipient, включая QuickLoot/AutoLoot; защищённые
  городские сундуки — **общий постоянный банк кампании** с identity скрытого backing container.
  Merchant stock пока личный.
- Первичная игровая база — установленная владельцем чуть более новая обычная RFAB.
  Она недоступна на GitHub: **не искать её и не выдавать публичные скрипты за её ABI**.
  Обновления и Bizarre — через capabilities/adapters, без универсальных обещаний.
- Полезные port/installer/report collector сохраняются после проверки. Старая тяжёлая обвязка
  не возвращается целиком. Все изменения остаются в текущей ветке этого репозитория.

Матрица раздела 7 остаётся матрицей приёмки **единого** кандидата. До полной production-связки,
автоматических проверок и Windows-сборки `ready_for_playtest=false`; успешный core/server test
сам по себе не разрешает публикацию незаконченного игрового релиза.
