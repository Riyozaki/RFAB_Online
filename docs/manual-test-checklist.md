# Чек-лист ручного тестирования в игре

Среда разработки не позволяет собрать и запустить клиент, поэтому всё
перечисленное ниже помечено как **требует проверки в игре**. Чек-лист составлен
так, чтобы каждый пункт давал однозначный «да/нет» и ссылку на место в коде,
где это реализовано.

## 0. Подготовка (один раз)

1. Убедиться, что у всех участников **одинаковые** версии: Skyrim SE 1.5.97.0.8,
   SKSE64 2.0.20, SE-база Address Library, один и тот же мод-лист RFAB.
2. Собрать клиент и сервер **из одного коммита** (см. `BUILD.md`).
3. Положить `RFABOnline.ini` в `Data/SKSE/Plugins/` (шаблон — в `GameFiles/`).
4. Включить логи (`Documents/My Games/Skyrim Special Edition/SKSE/*.log`,
   лог сервера) — почти все проверки подтверждаются строками в логе.

## 1. Один игрок (регресс: мультиплеер не должен менять одиночную игру)

| # | Шаг | Ожидание |
| --- | --- | --- |
| 1.1 | Зайти на сервер, найти бандита, посмотреть его HP | HP такой же, как в одиночной игре RFAB (×1) |
| 1.2 | Убить его | XP начислен штатно, в логе `Health scaling: 1 player(s) -> NPC health x1.00` |
| 1.3 | Проверить `PlayerXP` и полосу уровня | значения совпадают с одиночной игрой |
| 1.4 | Выйти, загрузить сохранение | соединение уже закрыто, `[Save]` работает, падения нет |
| 1.5 | Проверить `RFABOnline_saves_index.jsonl` | есть запись с `inSession:false` для одиночного сейва, старые сейвы не переразмечены |

## 2. Два игрока

| # | Шаг | Ожидание |
| --- | --- | --- |
| 2.1 | A и B рядом; A бьёт бандита (база 100 HP) | у обоих на экране/в актор-велью максимум **300**; лог `2 player(s) -> x3.00` |
| 2.2 | A добивает | XP у **обоих** одинаковый (B получает начисление, хотя не бил) |
| 2.3 | B читает книгу навыка | XP у обоих один и тот же, **без** двойного начисления у B |
| 2.4 | A выходит из игры в бою | B не «замерзает»: владение врагом переходит к B (`OwnershipTransferEvent` в логе), HP не скачет |
| 2.5 | A заходит обратно | максимум HP остаётся **×3**, не ×9 (проверка кэша базы по форме) |
| 2.6 | A уходит в другую ячейку, возвращается | HP врагов ×3 (не ×9) |
| 2.7 | B убивает врага, пока A в другой ячейке | опыт приходит обоим |
| 2.8 | Оба одновременно завершают один квест | каждому начислено **один раз**; в логе сервера максимум одно `suppressed duplicate amount` |

## 3. Три игрока

| # | Шаг | Ожидание |
| --- | --- | --- |
| 3.1 | Все трое рядом | максимум HP врагов **×4** (`3 player(s) -> x4.00`) |
| 3.2 | Один выходит | максимум пересчитывается в ×3, **доля HP сохраняется** (враг на 50 % остаётся на 50 %) |
| 3.3 | Убийство врага | XP одинаковый у всех трёх |
| 3.4 | Одновременное чтение книги всеми тремя | начислено каждому по одному разу |
| 3.5 | Смена владельца врага в бою (двое дерутся) | HP не дёргается, смерть приходит один раз |

## 4. Четыре игрока (максимум по умолчанию)

| # | Шаг | Ожидание |
| --- | --- | --- |
| 4.1 | Все четверо в одной ячейке | максимум HP **×5** |
| 4.2 | Двое в подземелье, двое в городе | у врагов **×5**: учитываются все подключённые игроки, а не только те, кто рядом¹ |
| 4.3 | Один дисконнектится во время загрузки | множитель не «прыгает» дважды, в логе одно пересчётное сообщение |
| 4.4 | Все выходят, затем заходят снова | база HP сброшена: первый враг снова ×N от ванильного значения |
| 4.5 | Один игрок с открытым меню (не в мире) | количество игроков считается по подключённым, а не по «в мире»¹ |

¹ Решение зафиксировано в `.work/ASSUMPTIONS.md`: `N` = число игроков,
подключённых к серверу (`PlayerManager::Count()`), включая тех, кто ещё
загружается. Если в игре окажется, что это мешает (например, множитель растёт
от игрока в главном меню), правится одна строка в
`HealthScalingService::OnUpdate`.

## 5. Плохая сеть и устойчивость

| # | Шаг | Ожидание |
| --- | --- | --- |
| 5.1 | Оборвать сеть у клиента на 10 с | после восстановления сессия жива или клиент корректно отключён; сервер не держит «мёртвого» владельца |
| 5.2 | Быстрый реконнект | `Sequence` начинается с 0, опыт не дублируется (`rejected replayed report` не в счёт) |
| 5.3 | Спам-клиент (тест-сборка), шлёт XP 10⁹ | сервер отклоняет: сумма > 100 000 отбрасывается |
| 5.4 | Клиент шлёт NaN в актор-велью | сервер пишет `dropped non-finite value`, актёр остаётся живым/нормальным |
| 5.5 | Клиент шлёт «мой персонаж умер» | сервер пишет `refusing to mark player character ... as dead` |

## 6. Сохранения

| # | Шаг | Ожидание |
| --- | --- | --- |
| 6.1 | Быстрое сохранение (F5) в сессии | через ~5–7 с одна запись в индексе, `inSession:true`, корректный `server` |
| 6.2 | Ручное сохранение поверх того же слота | новая запись, дублей нет |
| 6.3 | Загрузка сохранения в сессии | HUD «Save loaded - disconnected...», соединение закрыто, игра не падает |
| 6.4 | `bStopSessionOnLoad = 0`, загрузка в сессии | соединение остаётся, в логе предупреждение (режим для диагностики) |
| 6.5 | `bIndexSaves = 0` | индекс не пишется, остальное работает |

## 7. Что считать «провалом»

Любой из пунктов:

* HP врагов ×N² после смены ячейки или реконнекта;
* опыт начислен дважды одному игроку за одно событие;
* опыт не пришёл игроку, который не участвовал в событии;
* игрок «умер» от чужого пакета;
* вылет/зависание при дисконнекте владельца ячейки в бою;
* повреждённый `.ess` после сохранения в сессии.

При провале — приложить: лог клиента, лог сервера, строку из
`RFABOnline_saves_index.jsonl`, точный шаг из таблицы.
