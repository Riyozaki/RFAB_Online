# Ревью работы агентской ветки main (2026-10-22)

Объект ревью: `origin/main` @ `4cba32cd` — один коммит агента
(`WatermelonArbuz`), содержащий всё дерево нашей ветки
`arena/fcbffe0c-rfab-online` @ `396c5ab5` + дельту агента (52 файла).
Ревьюер: Arena-агент (автор Phase 0/Phase 1). Статусы: 🔴 блокер,
🟠 важно, 🟡 средне, ⚪ мелочь.

## TL;DR (вердикт)

Агент компетентен и сделал то, чего не мог сделать я в песочнице:
**собрал проект на Windows** (xmake 3.1.2) и прогнал тесты кодирования.
Его структурные выводы по 1.5.97 независимым путём (SKSE64-исходники и
CommonLibSSE) **совпали с моими Phase 1 правками** — это сильная
кросс-валидация. Он реализовал первые итерации HP-масштабирования и
синхронизации опыта RFAB, нашёл PSC-исходники RFAB и ловушку
EngineFixes в лаунчере.

Но: (1) обе фичи **отклоняются от принятой спецификации** (HP — ручной
статичный множитель вместо таблицы по числу игроков; XP — party вместо
всего сервера, без идемпотентности → двойные награды); (2) **10
mid-function патчей не портированы** — агент их вообще не упомянул, это
главный остающийся блокер запуска в игре, и это моя зона работ;
(3) процесс: вся история сплющена в один orphan коммит, в git попали
чужие бинарники (RFAB.esp 31 МБ и DLL) и подмодуль на репозиторий 3.1 ГБ.

У агента Skyrim SE **не установлен** (честно указано в его
`PHASE0_ANALYSIS.md`) — игровые тесты может выполнить только владелец.

## Находки

### 🔴 H1. Mid-function патчи не портированы (главный блокер запуска)
10 живых сайтов (`docs/phase-1-midfunction-audit.md`) до сих пор несут
смещения 1.6.x; агент их не трогал и не упоминал. Сборка проходит, но
клиент с высокой вероятностью упадёт при инициализации/первом
снаряде/рендере на 1.5.97. **Это моя работа**: нужен вывод
`tools/dump_patch_sites.py` с целевого `SkyrimSE.exe` (выполняет
владелец — у агента игры нет), дальше я пересчитываю 10 констант.

### 🔴 H2. main = один orphan коммит без истории
Вся предыстория (upstream 2975+ коммитов + наши Phase 1 коммиты)
сплющена; blame/бисект/будущие мерджи с форком на main невозможны;
нарушено правило атомарных коммитов. История цела на ветке
`arena/fcbffe0c-rfab-online`. Решение: пересобрать интеграцию поверх
нашей истории (дельта агента атомарными коммитами) — задача мне,
агент сверяет итоговое дерево со своим (tree-hash по `Code/`).

### 🔴 H3. Чужие бинарники и подмодуль-гигант в git
`RFAB_extract/RFAB.esp` (31 МБ, контент автора RFAB — не
распространять через наш публичный репозиторий), `skse64_1_5_97.dll`,
`tbb.dll`, `DINPUT8.dll`, `version-1-5-97-0.bin`; подмодуль `RFAB_ref`
→ весь `drake1ch/RFAB` (3.1 ГБ): наш `BUILD.md` велит
`clone --recursive` — новый разработчик выкачает гигабайты. Действие:
бинарники и подмодуль убрать из git, `refdata/` в `.gitignore` +
инструкция получения; TSV и мелкие конфиги перенести в
`docs/rfab-reference/` (производные данные, полезны).

### 🟠 H4. HP: статический множитель ≠ спецификация
Спецификация (решение владельца): множитель от числа игроков **на всём
сервере** (1→×1, 2→×3, 3→×4, 4→×5, N≥2→×(N+1)), таблица в конфиге
сервера, пересчёт при входе/выходе. Реализовано: ручная настройка
`Gameplay:fHealthMultiplier` (clamp 0.1–10), применяется владельцем
клиентски через `ForceActorValue(PERMANENT, kHealth)` с сохранением
доли HP, трекинг `AppliedHealthBonus`, восстановление ×1 при потере
владения. Механизм хороший, **политика неверная**: нет таблицы по
игрокам, нет пересчёта при join/leave, нет исключения игроков (нужно
доказать, что сущности игроков не получают `ActorValuesComponent`, и
в любом случае поставить явный guard), нет масок essential/summon,
сервер не является источником истины (хранит готовые значения
владельца). Действие: сервер вычисляет множитель по числу игроков и
рассылает (переиспользовать агентский канал `ServerSettings` + push при
join/leave). Дизайн + серверная логика — моя работа; клиентский
механизм агента переиспользуем.

### 🟠 H5. XP: область party ≠ решение «весь сервер»
Клиентский поллер и серверный relay ограничены party
(`SendToParty`, гейты `IsInParty`). Решение владельца — **все игроки
сервера**. Действие: настройка области (`server` по умолчанию,
`party` опцией), убрать клиентские гейты при `server`.

### 🟠 H6. XP: двойные награды (нет идемпотентности)
Агент честно обозначил отсутствие ledger/`AwardId`. Доказанный путь
дублирования по исходникам RFAB: `RFAB_XP_Alias.IsValidXPKill`
принимает убийцу из `PlayerFaction`/`IsPlayerTeammate` — на клиенте
второго игрока убийство партнёром может начислить XP **локально**, а
синхронизация добавит его ещё раз. Аналогично квесты: stage sync в ST
завершает квест на нескольких клиентах — каждый отправит дельту.
Нужен дизайн идентичности наград (убийства — `ServerId` жертвы,
квесты — quest+stage, книги/прочее — источник-событие) + серверный
ledger. Дизайн — моя Phase 4; агенту — замер/анализ фракций удалённых
игроков в ST. До дедупликации рекомендую `bEnableRfabXpSync=false` по
умолчанию (сейчас true).

### 🟠 H7. Восстановление HP при дисконнекте — риск краша
`ActorValueService::OnDisconnected` итерирует `view` и внутри вызывает
`ForceActorValue` (хуки могут разрушать компоненты; рядом в той же
функции — известный TODO про краш). Сначала собрать список сущностей.

### 🟠 H8. Серверный health sign bug не исправлен
`Code/server/Services/ActorValueService.cpp`:
`Current = currentHealth - message.DeltaHealth` при клиентской
конвенции «отрицательная дельта = урон» — серверное зеркало HP
инвертируется (находка моего Phase 0). Плюс нет проверки
`OwnerComponent == отправитель`. С агентским HP-хендоффом (вывод
предыдущего масштаба из серверных значений) это стало критичнее.
