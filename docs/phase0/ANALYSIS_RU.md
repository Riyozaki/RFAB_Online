# RFAB Online: анализ порта на Skyrim SE 1.5.97

Документ отвечает на восемь вопросов задания: что зависит от 1.6.x, что придётся
переписать, где именно сломается, какие места синхронизации слабые, что
конфликтует с RFAB, в каком порядке и за сколько это делать, что нельзя
проверить без игры и какие решения нужны от заказчика.

Всё, что помечено «проверено», проверено по исходникам, по базам Address
Library и по CommonLibSSE-NG. Всё, что касается поведения в игре, **не
проверено** и помечено явно: в среде разработки нет Windows и Skyrim.

---

## 0. Краткий вывод

1. **Порт реалистичен, но это не «поменять версию в конфиге».** Форк —
   это 42,9 тыс. строк клиента, 81 хук, 247 закреплённых смещений структур и
   3 083 идентификатора Address Library.
2. **Хорошая новость — раскладки структур.** 1.5.97 совпадает по памяти с
   1.6.318/1.6.353; сдвиг «+8» появился только в **1.6.629**. Отличий, которые
   нужно править, — **16 полей в 8 классах** (`docs/phase1/LAYOUTS_RU.md`).
3. **Хорошая новость — идентификаторы.** ID-пространства 1.5.97 и 1.6.x разные,
   но 2 978 из 3 083 ID, которые использует клиент, уже имеют точный
   перевод, подтверждённый сверкой с адресами 2021 года (`docs/phase1/README_RU.md`).
   Осталось 105.
4. **Главный скрытый риск — не ID и не структуры, а 14 сайтов патчей байтов
   внутри функций** (Nop/Put/SwapCall по смещениям `+0x53`, `+0x84E` и т. п.).
   Они привязаны к телам функций 1.6.1170 и на 1.5.97 почти наверняка
   не совпадут. Это отдельный поток работ, который нельзя закрыть пересчётом ID.
5. **Второй риск — отсутствие стенда.** Ни один пункт из фаз 1–5 нельзя
   считать выполненным без запуска на Windows + 1.5.97 + RFAB.
6. **Оценка: 80–160 человеко-дней** разработки плюс не менее 30 % времени на
   тестирование в игре. Подробности — раздел 6.

## 1. Что именно портируем

| Параметр | Значение |
|---|---|
| Источник | `rfortier/TiltedEvolution-rwf`, ветка `features-integration`, вершина `a7d06156` (2026-03-01) |
| Дельта к апстриму | 14 коммитов поверх `tiltedphoques/TiltedEvolution@dev` |
| Клиент | ≈ 42 900 строк `.cpp/.h`, 81 хук, 247 `static_assert` |
| Сервер | ≈ 7 600 строк, общий с 1.6.x, от версии игры не зависит |
| Кодирование/протокол | ≈ 12 200 строк, от версии игры не зависит |
| Целевая игра | Skyrim SE **1.5.97.0.8**, SKSE64 **2.0.20**, Address Library 1.5.97 (формат 1) |
| Целевая сборка | RFAB (`drake1ch/RFAB`): 51 мод, ≈ 62 SKSE-плагина, 14 плагинов NetScriptFramework, `RFAB.esp` 31,1 МБ, 1 365 `.pex` |

Сервер и протокол от версии игры не зависят вообще — это важное следствие:
**вся работа фазы 1 сосредоточена в клиенте**, а серверные фазы (3–5) можно
разрабатывать и тестировать без игры (симуляция на Linux).

## 2. Что зависит от 1.6.x

### 2.1. Address Library: 287 ссылок + 2 806 RTTI-идентификаторов

| Что | Количество | Где |
|---|---|---|
| `POINTER_SKYRIMSE(...)` | 269 | `Code/client/Games/**` |
| `VersionDbPtr<T> name(id)` напрямую | 18 | там же |
| `registerRtti_*` / `RttiLocator` (ID 392 214…414 675) | 2 806 | `Games/Skyrim/RTTI.cpp` |
| **Итого уникальных ID** | **3 083** | |

ID в Address Library **версионно-специфичны**: ID 38 936 в 1.6.x и в 1.5.97 —
разные функции. Без перевода каждый `POINTER_SKYRIMSE` указывает в случайное
место.

**Что делать:** таблица трансляции AE→SE + проверка при старте. Проверено:
2 978 ID (96,6 %) закрываются автоматически парами из CommonLibSSE-NG
(`RELOCATION_ID`, `REL::VariantID`), корректность подтверждена сверкой 2 805
пар с сырыми адресами дерева 2021 года — расхождений ноль. Осталось **105 ID**
(90 указателей, 13 `VersionDbPtr`, 2 RTTI).

**Стоимость:** 105 ID — 10–20 дней реверса, потому что каждый требует
дизассемблера и exe 1.5.97.

### 2.2. Раскладки структур: 247 утверждений, но править нужно 16 полей

`static_assert(offsetof(Actor, currentProcess) == 0xF8)` и подобные фиксируют
раскладку 1.6.1170. Проверка по CommonLibSSE-NG (`STATIC_ASSERT_SIZE`,
`RUNTIME_DATA_ACCESSOR_VERSIONED`) даёт точную границу:

```
ExtraDataList  0x18 (1.5.97) / 0x20 (1.6.629+)
TESObjectREFR  0x98 / 0xA0
Actor          0x2B0 / 0x2B8
PlayerCharacter +8 ко всем полям после базового класса
```

Всего 16 «версионированных» полей в 8 классах: `Actor` (6), `PlayerCharacter`
(4), `TESObjectREFR`, `BSAnimationGraphManager`, `CombatController`,
`TESObjectCELL`, `Inventory3DManager` (по 1). Дерево 2021 года подтверждает те
же 12 сдвигов `+0x8` у `Actor`.

**Что делать:** профиль сборки `1597` и `TP_LAYOUT(se, ae)` в утверждениях.
Оценка снижается с 15–25 до **3–5 дней**.

### 2.3. Патчи байтов внутри функций: 14 сайтов (главный риск)

Это то, что не видно в карте ID. Патчи ставятся по смещению внутри функции:

| Файл | Смещение | Что делает |
|---|---|---|
| `Games/Skyrim/BSGraphics/BSGraphicsRenderer.cpp:84` | `+0x174+1` | подменяет `dwStyle` окна на `WS_OVERLAPPEDWINDOW` |
| `…/BSGraphicsRenderer.cpp:90` | `+0x55+2` | снимает `DISCL_EXCLUSIVE` с DirectInput |
| `…/BSGraphicsRenderer.cpp:96` | `+9` | `SwapCall` таймера (`Hook_StopTimer`) |
| `…/Interface/Menus/MapMenu.cpp:13-15` | `+0x53`, `+0x9D`, `+0x9F` | отключает проверки карты |
| `…/Interface/Menus/SkillsMenu.cpp:12,14,16` | `+0x84E`, `+0xA10`, `+0x1040` | отключает обработку ввода в меню навыков |
| `…/SkillsMenu.cpp:20-21` | `+0x46`, `+0x4A` | то же для контролов |
| `…/Interface/UI.cpp:131` | `+0xFE` | `jmp` в инициализации UI |
| `…/UI.cpp:136` | `+0x15` | `nop` проверки избранного |
| `BSSystem/BSThread.cpp:84` | начало функции | ручной `Jump`-детур вместо MinHook |

Плюс два сайта в `#if 0` (`BSThread.cpp:89-95`), которые в сборку не попадают.

**Почему это риск:** смещения `+0x84E` и подобные описывают конкретные машинные
инструкции 1.6.1170. На 1.5.97 тело функции другое: патч либо не поставится
(и функция останется неотключённой), либо испортит соседнюю инструкцию и
уронит игру. Пересчёт требует дизассемблера и **обязательной** проверки в игре.

**Что делать:** на каждый сайт — либо пересчёт смещения под 1.5.97 (быстро, но
хрупко), либо замена на поиск по байтовой сигнатуре (паттерн-скан), который
работает на обеих версиях. Второй вариант дороже (5–10 дней), но убирает класс
проблем навсегда. Для `BSThread.cpp:84` достаточно заменить ручной `Jump` на
`TP_HOOK_IMMEDIATE` — механизм MinHook уже есть.

### 2.4. Явные проверки версии

| Место | Что сейчас | Что нужно |
|---|---|---|
| `Code/client/VersionDb.h:173,181` | ищет только `versionlib-*.bin`, читает только формат 2 | формат 1 (это 1.5.97) и оба имени файла |
| `Code/client/main.cpp:18,32` | диалог «All in one (1.6.X)» и `exit(4)` | сообщение с конкретной причиной |
| `Code/client/ScriptExtender.cpp:16,129` | `kSKSEMinBuild = 20100` (фактически не проверяет) | 2.0.20 для 1.5.97, 2.1.0 для 1.6.x |

Это самые дешёвые правки во всём порте (полдня), но без них дальше не пройти:
клиент просто не стартует.

### 2.5. RTTI и динамические приведения

`Games/Skyrim/RTTI.cpp` — 2 806 ID, которые используются для `Cast<T>` через
`TDynamicCast`. При неверном ID приведение вернёт мусор и уронит игру при
первом же обращении. Закрываются той же таблицей трансляции.

### 2.6. Чего в порте **нет** (хорошая новость)

* **Нет живых «сырых» адресов** вида `0x14XXXXXXX`: проверены все 9 вхождений,
  все либо в комментариях, либо в `#if 0`. Значит весь доступ к игре идёт через
  ID-слой — одна точка правки.
* **Нет байтовых сигнатур** (`Pattern`/`FindPattern`) — нечего перепроверять.
* Сервер, протокол и кодирование от версии игры не зависят.

## 3. Где именно сломается на 1.5.97

| # | Симптом | Причина | Диагностика |
|---|---|---|---|
| 1 | Диалог «Failed to load Skyrim Address Library», выход | нет файла `versionlib-1-5-97-0.bin`; читается только формат 2 | `VersionDb.h:181` |
| 2 | Клиент стартует и падает в первые секунды | `POINTER_SKYRIMSE` ведёт на чужую функцию | аудит ID при старте |
| 3 | Падение при первом обращении к актору | сдвиг `Actor::flags1` на 8 байт | профиль 1597 |
| 4 | Падение при открытии карты/меню навыков/избранного | патчи по смещениям не попали в инструкции | раздел 2.3 |
| 5 | Мусор при `Cast<T>` | ID RTTI от другой версии | таблица трансляции |
| 6 | «Тихо не работает» отключение проверок | патч применился к другой инструкции без падения | тесты в игре |

Сценарии 2, 4 и 6 опасны тем, что не дают явной ошибки: игра «работает», но
поведение не то. Поэтому в фазе 1 нужен не только аудит ID, но и журнал
применённых патчей с проверкой, что байты по целевому адресу совпали с
ожидаемыми.

## 5. Конфликты с RFAB

RFAB — не «чистая» игра: 62 SKSE-плагина и 14 плагинов NetScriptFramework
патчат те же функции, что и STR.

| Категория | Плагины RFAB | Риск для STR | Что делать |
|---|---|---|---|
| Патчи движка | `EngineFixes.dll`, `ScrambledBugs.dll`, `BugFixesSSE.dll`, `ActorLimitFix`, `AnimationQueueFix`, `FaceGenFixes`, `BackportedESLSupport` | **Высокий**: патчат память и ставят свои хуки на те же функции; порядок загрузки DLL определяет, кто кого перекроет | документировать порядок, тестировать вместе, при конфликте — исключать плагин |
| Анимации/поведение | `Nemesis`, `OpenAnimationReplacer`, `BehaviorDataInjector`, `AnimationMotionRevolution`, `DismemberingFramework` | **Высокий**: STR синхронизирует события анимаций; OAR подменяет анимации по условиям, которые у игроков разные | фаза 5: синхронизировать *события*, а не клипы; проверить, что OAR не ломает событие |
| HUD/UI | `TrueHUD`, `FloatingDamage*`, `HookDamage`, `SkyHUD`, `UIExtensions`, `moreHUD`, `QuickLootIE`, `MCMHelper` | **Средний**: конфликт ввода и фокуса с оверлеем STR (CEF + ImGui) | фаза 2: аккуратно с захватом ввода |
| Скриптовые расширения | `po3_PapyrusExtender`, `PapyrusUtil`, `ConsoleUtilSSE`, `PapyrusTweaks`, `DbSkseFunctions` | **Низкий/средний**: меняют Papyrus-среду, на которой держатся квесты RFAB | фаза 5: прогнать квестовые сценарии |
| XP/навыки | `CustomSkills`, `RFAB_XP_Handler.psc`, `Experience.ini`, `RFAB_XP_Settings.json` | **Высокий для фазы 4**: опыт выдаётся локальными скриптами | серверо-авторитетные события + локальное применение |
| Пауза/время | `SkyrimSoulsRE` | **Средний**: пауза меню в мультиплеере невозможна | решить политику (отключить или синхронизировать) |
| Баланс | `DifficultyBalance` | **Средний**: меняет урон/HP, конфликтует с масштабированием HP фазы 3 | единый источник истины на сервере |
| NSF | `NetScriptFramework` + 14 плагинов | **Средний**: отдельный фреймворк хуков | проверить двойное покрытие |

Отдельно про `RFAB.esp` (31,1 МБ): квесты, диалоги и скрипты завязаны на
FormID. При равном порядке загрузки FormID совпадают, но **порядок загрузки
сейчас не проверяется** (пункт 6 в разделе 4) — это надо закрыть в фазе 5
(«build-identity hash»).

## 6. План по фазам

Оценки — в человеко-днях одного разработчика, знакомого с C++ и SKSE.
Тестирование в игре не входит и идёт отдельным потоком (не менее 30 % времени).

### Фаза 1. Порт (40–80 дней)

| Задача | Дни | Приоритет | Риск |
|---|---|---|---|
| 1.1 Версионный слой и сборка: база форматов 1/2/5, оба имени файла, явные ошибки, профиль `1597` | 3–5 | P0 | низкий |
| 1.2 ID: таблица трансляции + аудит при старте + 105 ID вручную | 10–20 | P0 | средний (реверс) |
| 1.3 Структуры: 16 полей, 8 классов | 3–5 | P0 | низкий |
| 1.4 Патчи и хуки: 14 сайтов, 81 хук — проверка и пересчёт | 10–20 | P0 | **высокий** |
| 1.5 Стабильность: краши, утечки, гонки, обработка дисконнекта | 10–15 | P1 | средний |
| 1.6 Логи: уровни, ротация, журнал применённых патчей | 2–3 | P1 | низкий |
| 1.7 Сборка и документация (клиент/сервер, BUILD) | 3–5 | P1 | низкий |
| 1.8 Тесты: HP-формула, сериализация, передача владения | 3–5 | P2 | низкий |

**Критерий готовности фазы 1:** клиент запускается на чистой 1.5.97, аудит
показывает 3 083/3 083, игрок двигается и подключается к серверу; в логе нет
неприменённых патчей.

### Фаза 2. Качество синхронизации (10–20 дней)

Позиции, анимации, бой, смерть/респавн, инвентарь, экипировка, эффекты,
ячейки, загрузка/выгрузка акторов; владение акторами и передача при уходе,
смене ячейки, расстоянии, переподключении; интерполяция/экстраполяция, частота
обновлений, приоритизация по расстоянию; борьба с «призраками», застреваниями,
дублями, расхождением состояния смерти и лута.

Ключевые зависимости: пункты 1 и 2 из раздела 4 (здоровье и краши) должны быть
закрыты в фазе 1, иначе тестировать нечего.

### Фаза 3. Масштабирование врагов (8–15 дней)

* число врагов **не зависит** от числа игроков — генерация только из ванильных
  списков, без дополнительных спавнов и правки leveled lists;
* множитель HP на сервере: 1 игрок → ×1; 2 → ×3; 3 → ×4; 4 → ×5; N≥2 → ×(N+1);
  конфигурируемо;
* пересчёт при входе/выходе игрока **посреди боя** с сохранением отношения
  текущего HP к максимуму (без полного лечения и без мгновенной смерти);
* исключения (боссы, саммоны, essential) — конфигом;
* один авторитетный владелец врага, пакеты ИИ, цели, боевые состояния,
  анимации атак, урон, смерть, лут, опыт.

### Фаза 4. Опыт (8–12 дней)

Опыт начисляется всем игрокам одинаково, независимо от того, кто убил; интеграция
именно с XP-системой RFAB (скрипты `RFAB_XP_Handler.psc`, `CustomSkills`,
`Experience.ini`), а не с ванильным; идемпотентность по
`(actorId, deathRevision)`; корректность при переподключении и переходах между
ячейками; правила в конфиге сервера.

### Фаза 5. Адаптация RFAB (15–30 дней)

Квесты, враги, заклинания, анимации, механики XP, расы, перки, предметы,
скрипты; матрица совместимости «мод → влияние → требование → статус»;
политика квестов; синхронизация заклинаний и эффектов; события анимаций
(FNIS/Nemesis/OAR/DAR) и переменные поведения; FormID/порядок загрузки/ESL;
проверка идентичности сборки (хэш) с понятным сообщением; отдельный профиль
конфигурации «RFAB».

## 7. Что нельзя проверить без запуска игры

1. Любой из 14 сайтов патчей (раздел 2.3) — попал ли патч в инструкцию.
2. Корректность 16 смещений структур — читаются ли поля по правильным адресам.
3 Боевые механики: урон, смерть, лут, воскрешение.
4. Анимации и события анимаций в связке с Nemesis/OAR.
5. Квесты RFAB и Papyrus-скрипты.
6. Масштабирование HP «посреди боя».
7. Начисление опыта и его идемпотентность при переподключении.
8. Ввод/фокус при открытых меню и оверлее STR.
9. Утечки памяти на длинной сессии (2+ часа).
10. Поведение при разрыве соединения и повторном входе.

### Минимальный ручной чеклист (чистая 1.5.97, без RFAB)

1. Запуск: клиент стартует, в логе версия игры и итог аудита ID.
2. Новый персонаж, спавн в Хелгене, движение 60 секунд.
3. Подключение к локальному серверу, второй клиент, видимость друг друга.
4. Прыжки, бег, приседание, доставание оружия — анимации совпадают.
5. Бой: удар, получение урона, смерть, воскрешение.
6. Инвентарь: взять/выбросить/надеть предмет — видно второму игроку.
7. Переход в интерьер и обратно — без «призраков» и дублей.
8. Открытие карты, меню навыков, избранного — без падений.
9. Выход второго игрока — владение его NPC переходит корректно.
10. 30 минут в игре: нет роста памяти, нет падений.

### Затем то же на RFAB

11. Запуск через MO2 с профилем RFAB, все плагины RFAB загружаются.
12. Квест RFAB, диалог, применение заклинания, кастомный навык.
13. Убийство врага: опыт начислен обоим игрокам одинаково.
14. Босс: HP масштабируется при входе второго игрока посреди боя.
15. Смерть/расчленение (Dismembering Framework) синхронизируется.

## 8. Решения, которые нужны до начала фазы 1

**A. Поддерживать ли 1.6.x дальше.**
1. Только 1.5.97 (RFAB). Проще всего, апстрим отваливается.
2. Две сборки: профиль `1597` и профиль `1600` (текущее направление). Дороже
   на 15–20 % по времени, зато не ломает существующее.
3. Только 1.6.x, а RFAB перевести на 1.6.x (пересобрать RFAB под 1.6.1170).
   Радикально дешевле по коду, но это уже другой проект — пересборка 51 мода.

**B. Как считать опыт в фазе 4.**
1. Серверо-авторитетные события + локальное применение через API RFAB
   (`SetPlayerExperience` / `ModXP`), скрипты не трогаем.
2. Полный перенос XP-логики на сервер (скрипты RFAB отключаются).
3. Синхронизировать только ванильный опыт, а RFAB оставить локальным.

**C. Приоритет внутри фазы 1.**
1. «Играбельный минимум»: 1.1 → 1.4 → 1.5 (сначала запустить и стабилизировать),
   затем добить оставшиеся ID.
2. «Сначала всё ID»: 1.2 полностью (включая 105), потом всё остальное — дольше,
   но без сюрпризов «а этот ID мы не закрыли».

**D. Стенд.** Нужен компьютер с Windows, Skyrim SE 1.5.97 и RFAB. Без него можно
сделать примерно 50–60 % фазы 1 и серверную часть фаз 3–4, но нельзя объявить
готовой ни одну фазу.
