# RFAB Online — состояние проекта и почему он не стабилизируется

**Дата:** 2026-11-03 · **Ревизия:** `0b61c470` (`main`), релиз `v3.1.7` · **Автор разбора:** сессия Arena
**Статус документа:** единый живой документ о состоянии. Предыдущий разбор — `docs/AUDIT_2026-10-29_PROJECT_STATE.md` (висит в открытом PR #15); его выводы подтвердились, здесь они уточнены новыми измерениями и доведены до плана выхода.

Всё, что ниже, измерено на этой ревизии командами git/gh (не из документации проекта — документация проекту сейчас врёт, см. §4.4).

---

## 1. Главное в двух абзацах

Проект **технически живой и его база хорошая**: порт Tilted Evolution на Skyrim SE 1.5.97 сделан честно (структуры, Address Library, 3083 ID), протокол и сериализация чистые, установщик реально доводит человека до играбельного состояния. Это не «мусор, который надо выкинуть».

Но **способ работы с ним физически не может сойтись к стабильности**. За 9 дней в проект влили +69 500 строк C++ поверх реверс-инжиниринга движка, выпустили 31 релиз, при этом: единственный способ проверить изменение — запустить Skyrim руками; 28% «тестов» — это поиск подстрок в собственных исходниках; половина CI-прогонов красные; релизный артефакт не соответствует тегу, а UI в нём заморожен на v1.1.0. В такой схеме каждый новый фикс — это ставка вслепую: он с равной вероятностью чинит и ломает, а обратная связь приходит через плейтест спустя сутки. Отсюда ощущение «миллион фиксов, а проблем всё больше» — это не твоя ошибка в приоритетах, это **математика процесса**.

## 4. Четыре системных дефекта (с доказательствами)

### 4.1. Нет петли обратной связи — значит, нет инженерии

- **565 из 2026 проверок** — это буквально `CHECK(файл.find("строка") != npos)`. Пример из `rfab_v317_full_codebase_critical_audit.cpp`: проверяется, что в `Build-CloudRelease.ps1` присутствует текст `[string]$VersionTag = "v3.1.7"`. Такой тест зелёный, пока текст на месте, и краснеет от любого рефакторинга. Он не проверяет **ничего** о работе кода.
- Поэтому в истории есть коммиты вида `test: align VersionTag v3.1.4 contract assertions across historical suites` — тесты приходится «подгонять» под каждый релиз. Тест, который обслуживает релиз, а не наоборот.
- **Ни одного сценария «сервер + 2 клиента»** в CI. Сервер (`Code/server`) в CI вообще ни разу не запускается, хотя он платформенно-независим и его можно гонять на Linux за секунды.
- Следствие: **50% красных CI** и 15 коммитов «добавить `#include`» — код пишется вслепую, компилятор впервые видит его в облаке через 13–19 минут.

### 4.2. То, во что ты играешь, ≠ то, что лежит в git

- **UI заморожен на v1.1.0 (24.10).** `Package-Release.ps1` копирует готовый бандл из закоммиченного `dist_ready/.../UI` **через `/MIR` поверх** собранного — то есть даже если CI соберёт UI из `Code/skyrim_ui/src` (98 TS-файлов), его затрут старой копией. Последний коммит и в исходники UI, и в бандл — `71da3980` от 24.10.
- **Релиз пересобирается и перезаписывается на любой push.** Workflow триггерится на `arena/**` и `main`, вызывает скрипт с `-VersionTag "v1.0.0"`, скрипт «ремапит» защищённый тег в `v3.1.7` и заливает ассеты с `--clobber`. По API видно, что ассеты v3.1.7 загружены через час после создания релиза — другим прогоном.
- **Версия живёт в 5 местах и везде разная:** README — `2.0.3`, `RfabModpackCompat.h:22` — `2.0.0`, `release.yml:29` — `v1.0.0`, CHANGELOG — `3.1.7`, `package.json` — `1.0.0`.
- Практический вывод: когда в плейтесте вылезает баг, **нельзя достоверно сказать, какой код в этом билде**. Отладка в таких условиях — гадание.

### 4.3. Нет модели авторитета — вместо неё 113 таймеров

`kExternalDamageReconcileWindowMs = 650`, `kAmbushDedupWindowMs = 12000`, `kDefaultBarrierTimeoutMs = 12000`, `kDefaultReloadHostHoldMs = 15000`, `DematerializeGraceUntilMs`, `kPostDownedInFlightGraceMs`… Каждая константа — гипотеза «за N мс всё устаканится». Их 113, и они перемножаются: при другом пинге, FPS или числе игроков комбинация ломается, и добавляется 114-я.

Параллельно сосуществуют **три разных механизма владения**: `CoopOwnership` (89 упоминаний), `TakeOwnership`/`RequestOwnershipTransfer` (40), `OwnershipEpoch` (65) — без единого правила разрешения конфликта. Это прямой источник откатов HP, «двойных смертей», воскресших трупов и вайпов группы.

### 4.4. Архитектурный театр и дрейф документации

Каждый релиз объявлял «новую единую архитектуру», но старые слои не удалялись, а новые не доводились:

| Флагман релиза | Что с ним сейчас |
|---|---|
| `ServerInterestRegistry` (v2-stage1, «двунаправленный реестр интереса») | **8 упоминаний в 5 файлах**, из них половина — тесты |
| `RemoteEntityModel` (v2.1.0, «SSOT») | 10 упоминаний в 3 файлах |
| `FormView` / `WorldModel` (v2.0.1, «SkyMP-grade разделение») | 13 упоминаний в 2 файлах, по сути — комментарии |
| `ScopedLethalPlayerDamageIntercept` (v1.2.0, перехват летального урона) | **удалён в v3.0.0**; в коде остался только тест, требующий его отсутствия — **но README до сих пор описывает его как ключевую механику Downed-on-Knee** |

То есть README обещает пользователю механизм, которого в коде нет уже 4 релиза. При 33 документах в `docs/` (5.7 МБ), где несколько «финальных архитектур» противоречат друг другу, **сверяться не с чем** — а значит, каждая следующая сессия (человек или агент) начинает с неверной картины мира и делает ещё один слой.

## 6. Три варианта выхода

### Вариант A. «Чинить дальше по симптомам»
Продолжать как сейчас: плейтест → фикс → релиз.
**Цена:** 0 на старте. **Результат:** статистически предсказуемый — количество связей растёт быстрее, чем количество исправлений; через 10 релизов будет хуже, чем сейчас. **Рекомендация: нет.**

### Вариант B. «Сначала петля, потом авторитет» (план из PR #15, уточнённый)
1. **Фаза 0 (1–2 дня):** домерджить PR #15 (он зелёный) + включить `Tools/rfab/release-workflow.yml` вручную → релиз только по тегу, одна версия, чистый репозиторий, UI собирается в CI (а не копируется из `dist_ready`).
2. **Фаза 1 (3–5 дней, самое важное):** Linux-джоба для `server+encoding+common+tests` + **интеграционный харнесс «сервер в процессе + 2–3 клиента по loopback»**: вход/выход/реконнект, урон по NPC от двоих, смерть, лут без дюпа, передача владения, сейв-барьер с таймаутом, битые/обрезанные пакеты. Плюс удаление 565 подстрочных проверок.
3. **Фаза 2 (1–2 недели):** один протокол владения `{Owner, Epoch, Lease}` вместо трёх механизмов и 113 таймеров; хуки движка → только «снять событие»; логика → сервисы главного потока; знание о RFAB → в `RFAB_Online_Bindings.json`.
**Цена:** ~2–3 недели без новых фич. **Результат:** баг из плейтеста воспроизводится в CI за минуту, а не ловится игрой. Это единственный путь, после которого фиксы начинают накапливаться, а не компенсировать друг друга.

### Вариант C. «Откат к играбельному + сжатие фич» (можно совмещать с B)
Выбрать последний релиз, который реально игрался приемлемо (кандидаты по истории — `v1.2.0` или `v2.0.3`), объявить его базой, и переносить в него **только** те изменения v3.x, под которые есть воспроизводимый сценарий. Всё остальное (тактический HUD, пинги, часть RFAB-эвристик) — в отдельный флаг «экспериментально», выключенный по умолчанию.
**Цена:** 3–5 дней на перенос + решимость временно потерять фичи. **Результат:** быстро возвращается предсказуемость; дальше развитие идёт только через харнесс из Фазы 1.

**Моя рекомендация: C + B.** Сначала зафиксировать играбельную базу (C, чтобы было во что играть уже на этой неделе), параллельно построить петлю обратной связи (B, Фазы 0–1), и только потом трогать архитектуру владения (B, Фаза 2). Без петли любой вариант деградирует обратно за 2–3 релиза.

## 9. Сделано в этой сессии (ветка `arena/1c2d6190-rfab-online`)

Выбран курс **C+B** при базе **v3.1.x** (откат не нужен — текущая ветка признана лучшей).

### 9.1. Петля обратной связи появилась

`Tools/rfab/run-core-tests.sh` + `Tools/rfab/linux-core/Makefile` собирают и прогоняют платформенно-независимые слои (`TiltedCore` + `Code/encoding` + `Code/common` + переносимые Catch2-сьюты) обычным `g++`, без xmake, сабмодулей и Windows:

| | Было | Стало |
|---|---|---|
| Проверить правку в протоколе | push → 13–19 мин Windows-CI (50% красных) | **1.8 с** инкрементально, 1 мин 43 с с нуля |
| Что проверяется | наличие подстрок в исходниках | реальное выполнение кода |

Добавлена CI-джоба `.github/workflows/core-tests-linux.yml` — те же тесты на каждый push и PR.

### 9.2. Первый же прогон нашёл корневой баг в репликации таблицы строк

`CachedString` переносится в `ActionEvent`, `Tints`, `NotifyScriptAnimation`, `ScriptAnimationRequest` — то есть на горячем пути синхронизации анимаций и внешности. Fuzz-тест упал за 7 мс, разбор вскрыл три дефекта:

| # | Дефект | Последствие в игре |
|---|---|---|
| 1 | `CachedString::Deserialize` на неизвестный id делал `assert(false)` | debug — abort; release (`NDEBUG`) — поле **молча сохраняло прежнее значение** и уезжало дальше как валидное имя анимации/тинта |
| 2 | `StringCache::Deserialize` ассертил непрерывность, но в release **дописывал что угодно** | один несогласованный апдейт сдвигал все последующие id → до конца сессии каждый `CachedString` декодировался в чужую строку |
| 3 | Сервер слал обновления таблицы **только когда появились новые строки** (`if (!ProcessDirty()) return;`) | игрок, зашедший в уже прогретую сессию, таблицу **не получал никогда**, а сервер слал ему id → все `CachedString` у него пустые/чужие |
| 4 | `StringCacheUpdate::StartId` — `uint16_t`, таблица пополняется строками от клиентов без ограничения | >65535 записей → переполнение смещения и порча таблицы у всех |

**Исправлено:** неизвестный id → детерминированная пустая строка + счётчик диагностики (без abort и без «залипшего» значения); несогласованный апдейт отклоняется целиком (пробел / несовпадение перекрытия), повтор и перекрытие идемпотентны; сервер шлёт обновления по курсору каждого игрока, а не по флагу «появилось новое»; размер таблицы ограничен диапазоном wire-формата.

**Закреплено тестом:** `Code/tests/rfab_string_cache_protocol.cpp` — 7 поведенческих кейсов (поздний игрок, неизвестный id, пробел, повтор, несовпадение перекрытия, round-trip, граница 0xFFFF). Это первый тест в проекте, который проверяет **протокол**, а не текст исходников.

Итог прогона: `Passed all 17 test cases with 2658 assertions` (было: abort на первом же fuzz-кейсе).

### 9.3. Подтянута «Фаза 0» из PR #15

В ветку перенесены 4 коммита: единый `VERSION`, запрет перезаписи выпущенных релизов, wire-fuzz, удаление `build_logs_and_report/` (2.8 МБ) и `docs/rfab/rfab_records.tsv` (5 МБ). PR #15 после мержа этой ветки можно закрывать как поглощённый.

3. Сборка UI в CI вместо копирования `dist_ready/.../UI` через `/MIR`.
