**Дата:** 2026-10-29

**Что изучено:** история git (3117 коммитов), 32 GitHub-релиза, 50 последних CI-прогонов, структура 2105 файлов в индексе, ключевые модули `Code/client`, `Code/server`, `Code/encoding`, `Code/common`, `Code/tests`, пайплайн `Tools/rfab/*.ps1`, документация `docs/`.

## 0. Главный вывод (TL;DR)

Проект **не «почти готов»**, и проблема не в отдельных багах. Проблема в том, что **у проекта нет петли обратной связи и нет границ ответственности**:

1. **Тестов, проверяющих поведение, практически нет.** 40% всех проверок (258 из 644 `CHECK`) — это поиск подстрок в исходниках (`".find(\"kActorValueCount = 164\")"`). Они не проверяют работу кода, зато ломаются от любой правки текста и от смены номера версии. Зелёный CI означает «текст на месте», а не «код работает».
2. **Единственная реальная проверка — запустить Skyrim и поиграть.** Поэтому каждое исправление проверяется «на глазок», а следующая сессия добавляет ещё 10 эвристик поверх предыдущих. Сейчас в коде **107 захардкоженных таймингов** (окна, grace-периоды, кулдауны) — это прямая цена отсутствия модели авторитета.
3. **Слои перемешаны.** Знание про модпак RFAB вшито в 3926-строчный заголовок `Code/common/RfabModpackCompat.h` (парсеры JSON/INI/TOML/ESP, таблицы маркеров, UTF-8, проекция в экран — всё в одном файле). Игровая логика живёт внутри хуков движка. UI, инсталлятор, сервер, лаунчер и клиент лежат в одном репозитории без контрактов между ними.
4. **Релизный процесс фиктивный.** Любой push в ветку `arena/**` пересобирает и **перезаписывает ассеты «последнего» релиза** (`v3.1.7`), а «неприкосновенные» `-backup` релизы можно перезаписать тем же скриптом. Номер версии хранится в 5 местах и везде разный (README — `2.0.3`, `RfabModpackCompat.h` — `2.0.0`, `release.yml` — `1.0.0`, CHANGELOG — `3.1.7`, `package.json` — `1.0.0`).
5. **Проект нельзя собрать вне CI.** Сабмодули не инициализированы, а во время сборки скрипт **перезаписывает исходники сторонних библиотек** текстовыми заменами (`patch_submodules.py`). UI вообще не собирается — в релиз копируется заранее собранный `main.js` из закоммиченной папки `dist_ready/`.

Следствие: 154 коммита и **+195 000 строк за 9 дней**, **50% CI-прогонов красные** (25 из 50), 32 релиза за 8 дней. Это не «неаккуратность» — это структурная невозможность удержать проект в адекватном виде при таком способе работы. Дальше наращивать фиксы бессмысленно; нужно сначала построить фундамент: **тесты, сборку, авторитет, релизы**.

## 1. Что это за проект

- Форк **Tilted Evolution / Skyrim Together Reborn** (форк `rfortier/TiltedEvolution-rwf`), портированный с AE 1.6.x на **Skyrim SE 1.5.97.0.8** + SKSE 2.0.20, с адаптацией под модпак **RFAB (Requiem for a Balance)**.
- Стек: C++20, xmake 3.x, MSVC 2022, Windows-only для клиента; сервер/протокол — платформенно-независимые (могут собираться на Linux).
- Слои: `immersive_launcher` (подменяет `SkyrimSE.exe`) → `EarlyLoad`/`SkyrimTogether.dll` (хуки движка через `TiltedHooks`/`TiltedReverse`) → клиентские сервисы (`entt` registry + dispatcher) → транспорт `GameNetworkingSockets` → выделенный сервер.
- UI: CEF-оверлей (TypeScript, `Code/skyrim_ui`) + внутриигровой HUD на ImGui/D3D11.

**Что сделано действительно хорошо и что нельзя ломать:**

| Что | Где | Комментарий |
|---|---|---|
| Порт структур/смещений под 1.5.97 | `Code/client/Games/Skyrim/*` | `CombatController` (0xD8, без AE-спинлока), `ExtraDataList`, `TESObjectREFR`, `Actor` — соответствуют 1.5.97, проверено выборочно по коду |
| Address Library / version-*.bin | `TiltedReverse` + `docs/se-1597-id-map.csv` | 3083 ID переведены и зафиксированы CSV |
| Сериализация пакетов | `Code/encoding/` (254 сообщения) | Есть настоящие catch2-тесты (`Code/tests/encoding.cpp`) — единственная по-настоящему живая часть тестов |
| Структура сервисов | `World.cpp` | Понятный DI через `entt::registry`, сервисы с событиями — это правильный скелет |
| Разделение клиент/сервер/общее | `Code/{client,server,encoding,common}` | Хорошая база для выделения «кооп-ядра» |
| Лаунчер и установщик | `Code/immersive_launcher`, `Tools/rfab/Setup-RfabOnline.ps1` | Установщик реально доводит до играбельного состояния у пользователя |

## 5. Что на самом деле проверяют тесты

28 файлов в `Code/tests`, 104 `TEST_CASE`, 644 `CHECK`.

| Категория | Кол-во | Что делает |
|---|---:|---|
| Реальные поведенческие | ~386 | В основном сериализация/round-trip, `CoopLootLedger`, `SaveSnapshotCoordinator`, `CoopWorldView`. Полезно, но покрывает чистые структуры, а не интеграцию |
| **Поиск подстрок в исходниках** | **258** | `CHECK(srvAvCpp.find("kActorValueCount = 164") != npos)` |

Пример «теста» (`Code/tests/rfab_v317_full_codebase_critical_audit.cpp:227`):

```cpp
const std::string buildPs1 = LoadV317RepoFile(root, "Tools/rfab/Build-CloudRelease.ps1");
CHECK(buildPs1.find("[string]$VersionTag = \"v3.1.7\"") != std::string::npos);
CHECK(formsCpp.find("char buffer[1 << 15]") == std::string::npos);
```

Что это означает на практике:

- **Ложная зелёная зона.** Код может быть сломан логически — тесты пройдут, если строки на месте.
- **Тесты блокируют развитие.** Каждый релиз требует правки исторических тестов (`test: align VersionTag v3.1.4 contract assertions`, `v3.1.7`…). Тесты стали «замороженным текстом», а не защитой.
- **Ничего не проверяется про движок.** Ни один тест не воспроизводит сценарий «два клиента + сервер»: урон, владение, смерть, сейв-барьер, реконнект.
- Сервер (`Code/server`) в CI фактически не запускается ни разу.

## 6. Реестр проблем (по влиянию)

### Критические (архитектурные)

**F1. Нет модели авторитета — вместо неё таймеры.**
107 захардкоженных констант времени (`kMinWindowMs = 2500`, `kPostDownedInFlightGraceMs = 1500`, `pPredictionHoldWindowMs = 700`, `m_hostBarrierHoldRemainingSec = 6.0`, `DematerializeGraceUntilMs`, …). Каждая — гипотеза «через N мс всё устаканится». При смене FPS, лага, числа игроков гипотеза ломается, и добавляется новая. **Это корень «вайпов», откатов HP, двойных смертей и рассинхронов.**
*Нужно:* один протокол владения (epoch/lease), единственный писатель на сущность, детерминированные правила разрешения конфликтов. Таймеры — только как страховка, а не как логика.

**F2. Смешение слоёв «движок / игровая логика / знание мода».**
Правила RFAB (какие заклинания не бьют союзников, какие глобалы синхронизировать, как считать XP) зашиты в `common/RfabModpackCompat.h` (3926 строк, 25 из 65 «сырых» hex-адресов проекта) и в код боевых хуков. При этом в репозитории уже есть правильный механизм — `Data/SKSE/Plugins/RFAB_Online_Bindings.json`. Он не используется как единственный источник истины.
*Нужно:* всё знание о моде — в данные (+ схема + валидация), код — только интерпретатор. Тогда обновление RFAB не требует пересборки.

**F3. Бизнес-логика внутри хуков движка.**
`HookDamageActor` (213 строк), `HookAddTarget` (250), `HookRestoreActorValue` (178) содержат проверки режимов, леджеров, квестов. Хуки вызываются в произвольных потоках движка — отладить и протестировать это нельзя.
*Нужно:* хук = «снять состояние и отправить событие», вся логика — в сервисах на главном потоке.

**F4. Нет интеграционного теста.**
Ни одного сценария «сервер + N клиентов». Отсюда 50% красных CI и «проверка игрой».

**F5. Репозиторий и сборка невоспроизводимы** (см. §4, R1–R4, R9). Локальная сборка у разработчика с большой вероятностью отличается от CI.

### Высокие (процесс/поддержка)

**F6.** Фейковые «контрактные» тесты (258 проверок) — блокируют рефакторинг и создают ложную уверенность (§5).
**F7.** Релизный процесс: arena-бранчи публикуют релизы, «immutable» перезаписываемы, версия в 5 местах (§4, R4–R7).
**F8.** Документация: 5.7 МБ, 33 md-файла, README отстаёт на 4 релиза, аудиты противоречат друг другу и сами себе (несколько «финальных архитектур» подряд). Единого источника истины нет.
**F9.** Мёртвый вес: `dist_ready/` (9.3 МБ сборки), логи сборок, TSV на 5 МБ, дубли ассетов, `Code/one_ui` (второй Angular-UI, не используется в релизе).
**F10.** Год-файлы: `RfabModpackCompat.h` 3926, `CharacterService.cpp` 2792, `SaveSnapshotService.cpp` 1842, 52 функции > 120 строк. Читать и править такое без регрессий невозможно.

### Средние

**F11.** Нет наблюдаемости: нет структурированных событий/реплея, нет `/diag`-дампа, символы в отдельном 86-МБ архиве, разбор крашей — вручную. Логи игрока коммитили в git (149k строк) — значит, другого способа собрать данные не было.
**F12.** Самописный краш-декодер в `main.cpp` (SEH + разбор `ThrowInfo`) — хрупкая инфраструктура в точке входа.
**F13.** 65 «сырых» hex-адресов вместо Address Library; 23 файла с `TP_MAKE_THISCALL`; риск при любом обновлении движка/мода.
**F14.** Нет версионирования протокола: 254 сообщения, 0 упоминаний `ProtocolVersion` в `encoding/common` → клиент и сервер разных версий не отторгаются явно.
**F15.** Нет CI на Linux, хотя `server`/`encoding`/`common` платформенно-независимы → дешёвые интеграционные тесты недоступны (см. F4).

## 7. Почему «точечные фиксы» не работают

Каждый релиз `v3.0.0 → v3.1.7` — это набор из 6–12 «исправлений» вида «добавить guard», «добавить окно», «заморозить до N мс». Это лечит симптом в конкретной точке. Но:

- Поведение системы определяется **комбинацией** 107 таймеров и десятков флагов; проверить комбинации нельзя (нет тестов, нет модели).
- Каждый guard увеличивает связность: правка в бою ломает сейвы (`v3.1.6` чинил FIFO пакетов, `v3.1.5` — паузу меню, `v3.1.4` — потоки, `v3.1.3` — повозку…). Это классическая «латание дырявого корабля».
- Отсутствие тестов означает, что **регрессия обнаруживается игроком**, а не CI. Отсюда 25 красных прогонов и 32 релиза.

Стабилизация начнётся не с нового фикса, а с появления **способа проверять** и **одной модели авторитета**.

## 8. Что должно стать «адекватным»: 7 правил

1. **Один источник версии** (`VERSION`/`version.json`), из него — всё: сборка, UI, инсталлятор, релиз, README-бейджи.
2. **Собирается одной командой на чистой машине**, без правки чужих исходников; сабмодули — форки с коммитами (patch-скрипт удаляется), UI собирается в CI.
3. **Тест = поведение.** Никаких проверок «строка есть в файле». Взамен: unit-тесты ядра + интеграционный прогон «сервер + 2 клиента» в CI.
4. **Один владелец на сущность.** Явный протокол владения и разрешения конфликтов; таймеры — только как таймауты безопасности и в конфиге.
5. **Знание о RFAB — в данных**, не в коде.
6. **Релиз неизменяем.** Тег = коммит на `main` + зелёный CI. Ветки и PR дают только артефакты, не релизы.
7. **Наблюдаемость.** Структурированный лог событий + дамп состояния по команде + символы к каждому билду.
