# Ревью RFAB Online — 2026-10-22

**Что это за документ.** Полное ревью репозитория и кода после двух сессий:
порта TiltedEvolution-rwf на Skyrim SE 1.5.97 (предыдущий агент) и моей
проверки. Здесь: что проверено и как, что сделано хорошо, что сломано/не
доделано, матрица требований ТЗ и план работ по фазам.

Оценки честные: **ни одной сборки и ни одного запуска игры не было ни в одной
сессии** (Linux-песочница: нет MSVC, нет сабмодулей, нет xmake-пакетов, нет
самой игры). Всё, что ниже помечено как «работает», относится либо к коду,
прочитанному целиком, либо к оффлайн-проверкам, которые я реально прогнал.

| Область | Состояние |

| HP-скейлинг «2 игрока ×3, 3 игрока ×4» | **не сделано**: есть статический множитель из конфига, число игроков нигде не считается |

Главный риск проекта сейчас — не «баг в коде», а **отсутствие цикла
«собралось → запустилось → проверили»**. Пока его нет, любая доработка
синхронизации — это программирование вслепую.

## 3. Что сделано хорошо

1. **Порт ограничен по объёму и аккуратен.** Коммит `0f2ce79` — 33 файла,
   +842/−89. Нет «переписал всё», изменения точечные и в основном понятные.
2. **Явная проверка версии игры** (`Code/client/main.cpp:36-70`) вместо
   молчаливого запуска на неподходящем exe. При несовпадении — диалог и
   `exit 5` **до** установки хуков.
3. **SKSE проверяется по факту, а не по формуле.** `Code/client/ScriptExtender.cpp:14-19`:
   вайтлист file-version `{0,2,0,20}` вместо старого порога, который ошибочно
   отбраковывал 2.0.20 (проверялось по реальной `skse64_1_5_97.dll`).
4. **Address Library SE поддержана и проверена.** `Code/client/VersionDb.h:172-201`:
   принимаются имена `versionlib-*` и `version-*`, форматы 1 и 2. Формат 1
   декодирован тем же парсером до последнего байта (доказательство — в
   `docs/phase-0-evidence/`, я его воспроизвёл).
5. **Struct-ассерты как страховка.** 89 `static_assert(sizeof…)` и 173
   `offsetof` в `Code/client/Games` — если какая-то вложенная структура «поедет»,
   это будет ошибка компиляции, а не порча памяти в игре. Для порта это
   правильный подход.
6. **Тесты протокола добавлены** (`Code/tests/encoding.cpp`): round-trip для
   `ServerSettings` и двух новых сообщений XP. Пусть мало, но это первые тесты
   именно новых фич, а не только upstream'а.
7. **Документация честная.** Есть раздел «Errata» с признанием трёх ошибок
   Фазы 0, есть явные пометки «не проверено». Это редкость и это надо беречь.
8. **Оффлайн-инструменты воспроизводимы.** `tools/address_db_check.py` и
   `tools/dump_patch_sites.py` работают без игры и без сборки — на них можно
   строить проверяемые утверждения (я так и делал).

## 4. Проблемы

### 4.1. P0 — блокеры (без этого дальше нет смысла)

#### 4.1.1. Цикла сборки нет вообще

- `.github/` содержит только `workflows-upstream-disabled/` — CI отключён.
- `BUILD.md` при этом ссылается на `linux.yml`/`windows.yml`, которых в
  активных воркфлоу нет.
- Сабмодули в этом checkout не инициализированы (пустые каталоги), т.е.
  клонирование «как есть» даже не даст конфигурацию xmake.
- Версия xmake расходится: `BUILD.md` говорит 2.9.8, на машине предыдущей
  сессии был 3.1.2 (см. `docs/archive/…`).

**Значение:** любой коммит сейчас — «непроверенная правка». Первый приоритет —
не фичи, а красная кнопка: сборка сервера в CI + сборка клиента у вас на
Windows + лог первой загрузки.

#### 4.1.2. Десять внутрифункционных патчей остались от 1.6.x

Места, где код патчит **середину** функции по смещению (смещения зависят от
компиляции конкретного exe):

| Файл:строка | Патч |
|---|---|
| `Games/Skyrim/BSGraphics/BSGraphicsRenderer.cpp:84` | `Put` по `+0x174+1` |
| `…/BSGraphicsRenderer.cpp:90` | `Put` по `+0x55+2` |
| `…/BSGraphicsRenderer.cpp:96` | `SwapCall` по `+9` |
| `Games/Skyrim/BSSystem/BSTaskletManager.cpp:35` | `SwapCall` по `+0x63` |
| `Games/Skyrim/Interface/UI.cpp:126` | `SwapCall` по `+0x682` |
| `…/UI.cpp:131` | `Put 0xEB` по `+0xFE` |
| `…/UI.cpp:136` | `Put 0x9090` по `+0x15` |
| `Games/Skyrim/Interface/Menus/SkillsMenu.cpp:12,14,16` | `Nop` по `+0x84E/+0xA10/+0x1040` |
| `…/SkillsMenu.cpp:20,21` | `Nop` по `+0x46/+0x4A` |
| `Games/Skyrim/Projectiles/Projectile.cpp:130-153` | `Jump +0x374`, возврат `+0x379`, кадр стека `rsp+0x50/0x138` |

**Почему это P0:** эти патчи ставятся до первого кадра, и неверное смещение
означает либо молчаливое повреждение кода, либо краш на запуске — причём
диагностировать его вы будете по краш-логу NetScriptFramework, без шансов
понять, что это «наш» патч.

**Что делать:** снять байты вашим `tools/dump_patch_sites.py` с реального
`SkyrimSE.exe` 1.5.97, дизассемблировать окрестности стартов функций (ID из
Address Library уже известны) и либо пересчитать смещения, либо заменить на
**паттерн-скан с проверкой байтов и fail-safe**: не совпало — не патчим,
пишем `warn`, игра запускается. Второй вариант правильнее для «стабильно на
старых версиях».

#### 4.1.3. `TESObjectCELL` собран из двух разных портов

В репозитории реально существовали две независимые попытки порта
(`0f2ce79` и `7dfe1a0`), и merge взял для `TESObjectCELL` **не ту** версию,
что для остальных структур:

- `Actor` / `TESObjectREFR` / `PlayerCharacter` — версия `0f2ce79` (сдвиг на −8
  от 1.6.x: `Actor` 0x2B0, `TESObjectREFR` 0x98).
- `TESObjectCELL` (`Code/client/Games/Skyrim/Forms/TESObjectCELL.h`) — версия
  `7dfe1a0`: остались `uint8_t cellFlags[5]`, `struct LoadedCellData` с
  `encounterZone` на `+0x160` и **AE-раскладка `ReferenceData` (0x30, `uint64 unk0`)**,
  а всё после неё сдвинуто на −8 «вручную».

Ассерты внутри файла самосогласованы (`refData == 0x80`, `worldspace == 0x120`,
`sizeof == 0x140`), поэтому **сборка, скорее всего, пройдёт** — и это хуже:
ошибка проявится в игре на загрузке клеток, а не на компиляции.

Отдельно сомнительно:

- `bool IsValid() const { return cellFlags[4] == 7; }` — чтение пятого байта
  массива флагов как «состояния клетки»;
- `Actor.cpp:197` и `TESObjectREFR.cpp:309` проверяют `cellFlags[0] & 1`;
- `ExtraDataType::EncounterZone = 0x70` и `ExtraEncounterZone` добавлены, но
  нигде не используются, а encounter zone по-прежнему достаётся через
  `LoadedCellData`.

**Что делать:** выбрать одну раскладку (я бы взял версию `0f2ce79` — она
структурная, а не «сдвиг на 8»), сверить с CommonLibSSE-SE (1.5.97) и, главное,
с дампом из вашего exe по ID `TESObjectCELL`-функций. До этого клеточные
операции считаем непроверенными.

#### 4.1.4. Нет версии протокола, а формат сообщений уже изменён

- В `ServerSettings` добавлено поле `float HealthMultiplier` (в конец — хорошо),
  но `ServerSettings::operator==` (`Code/encoding/Structs/ServerSettings.cpp:8`)
  **забыл** `SyncPlayerCalendar` (баг пришёл из upstream-ревертов, но он живой:
  смена только календарной настройки не считается изменением).
- Добавлены 2 опкода: `kSyncRfabExperienceRequest` (`Opcodes.h:58`),
  `kNotifySyncRfabExperience` (`Opcodes.h:121`) — оба в конце enum, фабрики
  обновлены, тесты есть. С точки зрения «наш клиент ↔ наш сервер» — ок.
- Но! Единственная защита совместимости — сравнение git-хеша сборки
  (`BUILD_COMMIT`, `GameServer.cpp:874`). Это значит: любой ребилд с другим
  коммитом ломает коннект, а семантика протокола нигде не зафиксирована.

**Что делать:** ввести `constexpr uint32_t kProtocolVersion` (и инкрементировать
его при несовместимых изменениях), логировать обе версии в отказе; в
`AuthenticationResponse` передавать `protocolVersion` + `buildCommit`.
Починить `operator==`.

#### 4.1.5. HP-скейлинг не соответствует ТЗ

Требование: «2 игрока → ×3 HP, 3 игрока → ×4; количество врагов не растёт».
Фактически (`Code/client/Services/Generic/ActorValueService.cpp:139-170`):

```
newMax = (currentMax − AppliedHealthBonus) × M,  M = ServerSettings.HealthMultiplier (конфиг)
```

- `M` — **статическая настройка сервера** `Gameplay:fHealthMultiplier`
  (`Code/server/GameServer.cpp:49`), по умолчанию **1.0**, то есть по умолчанию
  фича выключена.
- **Число игроков не считается нигде** (проверено grep'ом по серверу: есть
  только `uMaxPlayerCount`, лимит подключений).
- Скейлинг **клиентский**: сервер лишь раздаёт множитель, а применяет его
  владелец актора. Значит «истины» на сервере нет; поздно вошедший игрок
  получает те значения, которые последним прислал владелец.
- Скейлятся **все** owned-акторы без фильтров: саммоны, эссенциальные NPC,
  трупы (`IsDead()` не проверяется), животные. «Не воскрешать мёртвых» из
  плана Фазы 0 не реализовано.
- Пересчёт идёт **раз в секунду** по всем owned-акторам
  (`ApplyHealthScaling()` вызывается из `RunActorValuesUpdates`). Формула
  идемпотентна (повторный вызов — no-op), но это лишняя работа и лишние
  сетевые `NotifyActorMaxValueChanges`.
- `ForceActorValue(PERMANENT, …)` меняет **базовое** значение актора. Для
  постоянных (persistent) референсов такие изменения могут попасть в сейв —
  при краше клиента «раздутые» HP останутся в сохранении. На disconnect/потере
  владения откат есть (`OnDisconnected`, `OnLocalComponentRemoved`), но не при
  краше/выключении питания.

**Что делать (дизайн, который закрывает требование и не ломает игру):**

1. Сервер — источник истины: считает `N` (см. открытые вопросы §8) и
   `M = min(N + 1, cap)` (N=2 → 3, N=3 → 4), при изменении `N` рассылает
   `NotifySettingsChange`.
2. Сервер хранит **базовый** `maxHealth` актора отдельно от масштабированного
   (`ActorValuesComponent` → добавить `BaseMaxHealth`), а в `CharacterSpawnRequest`
   отдаёт уже масштабированное значение. Тогда поздно вошедший видит
   правильный HP без гонок владения.
3. Применять только к NPC: `!IsPlayer`, `!IsPlayerSummon()` (конфигурируемо),
   `!IsDead()`, и, желательно, не к «essential/quest item» без отдельного флага.
4. Хранить процент здоровья и **не трогать мёртвых**; при смерти — снимать
   скидку/надбавку, а не «восстанавливать» HP.
5. Юнит-тесты на формулу и на пересчёт процента — на сервере, без игры.

#### 4.1.6. «Равный опыт» реализован как пересылка дельт, а не как события

Что есть сейчас (`Code/client/Services/Generic/CharacterService.cpp`):

- клиент раз в секунду читает `TESGlobal` `RFAB_XP_Amount` (BaseId `0xAD45BB` —
  я проверил по `rfab_records.tsv`, такой глобал в `RFAB.esp` **действительно
  есть**), считает дельту и шлёт `SyncRfabExperienceRequest`;
- сервер (`Code/server/Services/CharacterService.cpp:544`) пересылает её
  **остальным членам партии** (не «всем игрокам сервера»);
- получатель прибавляет дельту к своему глобалу и вызывает
  `Game.SetPlayerExperience(GetPlayerExperience() + delta)`.

Проблемы:

1. **Область не та.** Решение зафиксировано «весь сервер», код делает «партия».
2. **Нет идемпотентности и дедупликации.** Любое дублирование события даёт
   двойной опыт: например, один и тот же квест синхронизируется обоим игрокам →
   каждый получит квестовый XP и разошлёт его → у всех двойной. Аналогично
   книги/боссы.
3. **Нет привязки к основаниям.** В RFAB XP начисляется событиями
   (`RegisterForActorKilled`, `OnQuestComplete`, книги `BaseBookXP=200`,
   боссы +1000 из `BossList.json`, множитель `MultiplierXP`, капы уровней).
   Пересылка дельт не знает, **за что** опыт, поэтому сервер не может ни
   проверить, ни дедуплицировать, ни начислить «каждому по одному разу».
4. **Обход пайплайна RFAB.** Запись напрямую в глобал + `SetPlayerExperience`
   не проходит через скриптовый хендлер сборки: возможны расхождения
   (перк-поинты, UI, капы, `StorageUtil`-счётчики), и это надо проверять в игре.
5. **Наличие Papyrus-функций не проверено.** Если `Game.SetPlayerExperience`
   в 1.5.97 нет, фича молча пишет `warn` и не работает; fallback отсутствует.
6. **Ванильный skill-XP по-прежнему теряется** при
   `PlayerCharacter::LastUsedCombatSkill == -1` (`CharacterService.cpp:966-971`) —
   то есть половина «опыта» (навыки) остаётся несинхронизированной.

**Что делать:** перейти на **серверные события-основания** с дедупликацией
(`KillCredit{victimServerId}`, `QuestComplete{questId}`, `BookRead{bookId}`,
`BossKill{bossId}`) и ключом идемпотентности (session + seq), а на клиенте
начислять опыт **через собственный RFAB-пайплайн** (вызвать его Papyrus-функцию
или воспроизвести расчёт по тем же таблицам). Для этого нужно понять, где RFAB
хранит накопленный XP — требуется декомпиляция `RFAB_XP_Handler.pex`/
`RFAB_XP_Alias.pex` (Champollion) или исходники от автора сборки.

### 4.2. P1 — синхронизация и логика

1. **Знак HP на сервере (баг оригинала).**
   `Code/server/Services/ActorValueService.cpp:88`:
   `ActorValuesList[24] = currentHealth - message.DeltaHealth`, при том что
   клиент шлёт урон отрицательной дельтой. Серверная копия HP при уроне
   **растёт**. Она же уходит поздно вошедшим при спавне. Это готовый рецепт
   «враг с полным HP у нового игрока» и «воскресший NPC».
   Плюс `[24]` — магический индекс вместо `ActorValueInfo::kHealth` (сам индекс
   верный, но читаемость нулевая).
2. **Нет проверки владельца.** Все четыре обработчика `ActorValueService`
   (сервер) принимают значения от любого клиента и ретранслируют
   (`view<…, OwnerComponent>` проверяет только то, что владелец существует).
   Любой клиент может менять HP/AV чужого NPC. Это и источник «войны за NPC»,
   и потенциальный чит.
3. **`OnHealthChangeBroadcast` (клиент)** по-прежнему убивает актора, если
   `health <= 0` и это не игрок, — то есть смерть определяется получателем,
   а не владельцем; при рассинхроне это даёт двойные смерти/респавны.
4. **ModPolicy.** `bEnableModCheck` по умолчанию `false`
   (`Code/server/GameServer.cpp:51`), описание настройки инвертировано
   («Bypass the checking…» при `false`), проверки порядка/хеша плагинов нет.
   Для RFAB с 23 плагинами и ~61 SKSE-DLL это прямой путь к десинку, который
   потом спишут на «плохую синхронизацию».
5. **Смерть/респавн игроков и `NotifyDeathStateChange`** — не проверялось
   в игре; после HP-скейлинга трогать аккуратно.

## 6. План работ

Порядок — по зависимостям, а не по «интересности». Критерий каждой фазы —
измеримый, иначе это не фаза, а намерение.

### Фаза A — «оно вообще запускается» (критический путь)

1. Инициализировать сабмодули, зафиксировать рабочий рецепт xmake
   (2.9.8 или 3.x — выбрать и записать в `BUILD.md`).
2. Включить CI: Linux-сборка сервера + `Code/tests` (Catch2) в GitHub Actions.
   Это единственное, что можно проверить без игры и без Windows.
3. Windows-сборка клиента у вас → прислать лог ошибок компиляции (первым делом
   ожидаю `static_assert` — это нормальный сторожевой срабат).
4. Снять дамп патч-сайтов с вашего `SkyrimSE.exe`:
   `python3 tools/dump_patch_sites.py "…\SkyrimSE.exe" > patch-sites.txt`.
5. Пересчитать 10 патчей или перевести их на паттерн-скан с fail-safe.
6. Первый запуск по чек-листу: меню → база 1.5.97 в логе → «SKSE is active» →
   новая игра → коннект к локальному серверу → второй клиент видит первого.

**Готово, когда:** два клиента стабильно сидят на сервере 30 минут без крашей,
в логах нет ошибок Address Library/SKSE, и есть воспроизводимый CI-зелёный
статус на серверной части.

### Фаза B — синхронизация починки (P1)

1. Знак HP на сервере (`ActorValueService.cpp:88`) + тест на пересчёт.
2. Проверка владельца во всех четырёх обработчиках AV (`acMessage.pPlayer` ↔
   `OwnerComponent`), отказ с логом вместо ретрансляции.
3. `kProtocolVersion` + логирование обеих версий при отказе коннекта.
4. Починить `ServerSettings::operator==` (`SyncPlayerCalendar`).
5. Включить `ModCheck` для RFAB-профиля (список 23 плагинов, затем хеш
   loadorder в handshake — уже с новым protocol version).

**Готово, когда:** в игре урон по NPC не «лечит» их у поздно вошедшего игрока,
украсть/испортить HP чужого NPC нельзя, а несовпадение сборок даёт понятную
ошибку, а не загадочный десинк.

### Фаза C — HP-скейлинг по числу игроков (требование №5)

Дизайн — в §4.1.5. Дополнительно:

- конфиг `Gameplay:bEnableHealthScaling` (вкл/выкл), `Gameplay:uHealthScalingCap`,
  `Gameplay:eHealthScalingTarget` (server / in-cell / party), формула
  `M = N + 1` с округлением и cap;
- сервер хранит `BaseMaxHealth` отдельно от текущего, пересчитывает при
  изменении состава игроков и при спавне;
- фильтры: не игроки, не саммоны (опция), не мёртвые, не «essential» (опция);
- юнит-тесты: `N=1→1, N=2→3, N=3→4, N=8→cap`, сохранение процента, `0 HP → 0`,
  мёртвый не воскресает.

**Готово, когда:** тест в игре на 1/2/3 игроках показывает ожидаемые HP и
одинаковый HP-бар у всех, а после дисконнекта значения возвращаются к базовым.

### Фаза D — опыт (требование №4)

1. Декомпилировать `RFAB_XP_Handler.pex`/`RFAB_XP_Alias.pex`, найти место
   хранения XP и точку входа начисления. Без этого — только гипотезы.
2. Сервер: события `KillCredit`, `QuestComplete`, `BookRead`, `BossKill` с
   дедупликацией по `(sessionId, sequence)` и журналом в рамках сессии.
3. Клиент: начисление через RFAB-пайплайн, а не через `SetPlayerExperience`
   напрямую (если пайплайна не достать — расчёт по тем же таблицам
   `RaceList.json`/`Experience.ini`/`Quests.ini` на сервере, с клиентом как
   исполнителем).
4. Область — по решению (§8): весь сервер или партия.
5. Починить skill-XP: передавать `skillId` в сообщении, а не полагаться на
   `LastUsedCombatSkill` получателя.

**Готово, когда:** убийство одного NPC одним игроком даёт ровно один и тот же
опыт всем; квест, выполненный одним, даёт опыт всем один раз; реконнект не
дублирует; уровни/перк-поинты совпадают у всех.

### Фаза E — RFAB-совместимость (требование №8)

1. `ModCheck`-пресет «RFAB»: 23 плагина + проверка порядка; серверу — копии
   файлов плагинов в `mods/` для `RecordCollection`.
2. Дескрипторы поведений (`GameFiles/…/SkyrimTogetherRebornBehaviors/`) под
   Nemesis-графы RFAB: сгенерировать по факту HKX у вас и добавить.
3. Решить конфликт `SkyrimSoulsRE.dll` ↔ наши патчи №7–9 (StatsMenu/избранное):
   либо отключать наши при наличии мода, либо отключать опции в его ini.
4. DifficultyBalance vs серверный `uDifficulty`: один источник истины.
5. `RFAB.dll` — статический аудит строк/импортов уже делался; дальше только
   эмпирика (включение/выключение, тесты боя) + запрос исходников автору.

### Фаза F — наблюдаемость и тесты

- структурированные логи: модуль + уровень на модуль, ротация на сервере;
- дешёвый «диагностический» режим: команда сервера, печатающая расхождения
  (HP, ownership, XP) — по нему вы будете присылать отчёты без скриншотов;
- тесты: серверная логика (формула HP, дедуп XP, знак урона) — Catch2, без игры.
